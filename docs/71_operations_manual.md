# 71. Seller OS 운영 매뉴얼

이 문서는 **매일 실제로 무엇을 하는지**를 적은 것이다. 설계 문서가 아니다.

> 판매처 API 는 아직 대부분 연결되지 않았다. 아래 절차에 사람이 하는 입력이
> 섞여 있는 이유다. 커넥터가 붙으면 ★ 표시한 것들이 사라진다.
>
> **NEXT ENGINE 주문은 자동 수집으로 넘어갔다.** 상품 연결까지 끝났고, 주기가
> 되면 워커가 스스로 읽어 판매장부에 넣는다. 사람이 매일 할 일이 없다 —
> 아래 1-★ 참조. 다만 **운영 서버에서 워커 스케줄러를 켜야** 실제로 주기
> 실행된다(설치 전에는 수동 실행·화면의 [지금 동기화] 로 돈다).

## 0. 처음 한 번만 — 시작 설정

순서대로 해야 뒤엣것이 돌아간다.

### ① 상품에 소싱처 연결 (★ 가장 먼저)

**이걸 안 하면 재주문이 통째로 안 돈다.** 현재 상품 1,065개 중 연결된 것이
0개다.

```
사이드바 → 소싱 → 소싱 연결
```

화면 위쪽이 "무엇이 비었는지" 를 숫자로 보여준다. 파일은 CSV/XLSX 어느 쪽이든
된다.

| 열 | 필수 | 예 |
|---|---|---|
| SKU 또는 상품번호 | ✅ 셋 중 하나 | `PICK0785` / `PROD-000123` |
| 공급처코드 또는 공급처도메인 | ✅ 둘 중 하나 | `DOMEGGOOK_COM` / `domeggook.com` |
| 공급처URL | | `https://domeggook.com/item/123` |
| 리드타임 | | `7` (일) |
| MOQ | | `10` |
| 주소싱처 | | `Y` |
| 매입가 | | `3000` |

**이름으로는 찾지 않는다.** 비슷한 이름을 잘못 맞추면 엉뚱한 공급처의 원가로
발주가 나가기 때문이다. 못 찾은 행은 "상품 못 찾음" 으로 나오고 반영되지 않는다.

리드타임·MOQ 를 모르면 **비워 둔다.** 임의로 채우면 그 숫자로 발주 시점이
계산된다.

> 검토 → 결과 확인 → 적용. 파일을 고르면 검토까지만 자동으로 돈다.

### ② 초기 재고 넣기

```
사이드바 → 재고·재주문 → [재고 가져오기]
```

| 열 | 필수 |
|---|---|
| SKU 또는 상품번호 | ✅ |
| 수량 | ✅ |
| 기준일 | 실사한 날 |

수량은 **목표 잔량**이다. 원장이 없으면 최초 재고로, 있으면 차이만큼 조정으로
들어간다. 같은 파일을 두 번 올려도 재고가 두 번 늘지 않는다.

### ③ 재주문 기준 정하기

```
설정 → 자동화 → 재주문 감시
```

두 값을 정해야 재주문이 계산된다. **기본값이 없다** — 적정 재고는 사업마다
다르고, 화면에 뜬 숫자가 어디서 왔는지 알아야 하기 때문이다.

```
판매속도 관찰 기간   최근 며칠의 판매로 속도를 볼 것인가
목표 커버 일수       발주로 며칠치를 확보할 것인가
```

회전이 빠르면 관찰 기간을 짧게, 시즌을 타면 길게 잡는다.

### ④ 일일 리포트 켜기

```
설정 → 자동화 → 일일 운영 리포트 → 사용
```

매일 한 번 리포트를 만들고 앱 알림으로 알려준다. 이메일은 아직 안 된다
(SMTP 미연결 — 안 보내면서 보냈다고 하지 않으려고 꺼 뒀다).

## 1. 매일 — 5분

### 켜기 · 끄기 (개인 PC 운영)

서버가 없으므로 **PC 를 켜야 Seller OS 가 돈다.** 꺼진 컴퓨터가 아무것도
안 하는 것은 고장이 아니다.

```
PC 를 켠다
  ↓
바탕화면 [Seller OS 시작]        ← 한 번이면 끝이다
  ↓
브라우저가 오늘의 운영을 연다
  ↓
창에 따라잡기 결과가 찍힌다       ← 아래 참고
  ↓
PC 를 끄기 전 [Seller OS 종료]
```

바로가기가 없으면 한 번만:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\install_local_shortcuts.ps1
```

### 며칠 PC 를 안 켰다면 — 자동으로 따라잡는다

시작할 때 **꺼져 있던 기간의 주문·취소·반품을 스스로 읽는다.** 18일이든
한 달이든 상관없다. 벤더 한도(10일)에 맞춰 나눠서 읽고, 이미 받은 건은
다시 만들지 않는다. 사람이 날짜를 지정할 일이 없다.

시작 창 마지막에 이렇게 찍힌다.

```
  주문        OK    조회 1 · 신규 0 · 갱신 0 · 변화없음 1
  클레임      OK    조회 16 · 신규 0 · 갱신 0 · 변화없음 16
  일일리포트  2026-08-17 생성됨
  데이터 최신성  OK
```

### 데이터가 최신인지 따로 확인한다

**앱이 열렸다고 데이터가 최신인 것은 아니다.** 둘은 다른 사실이다.

```
화면 → 운영 → 시스템 상태 → "데이터 최신성"
```

주문과 취소·반품의 **마지막 성공**과 **마지막 시도**를 따로 보여준다.
마지막 시도는 있는데 마지막 성공이 오래됐다면, 계속 실패하고 있다는 뜻이다.

터미널에서 한 번에 보려면:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\status_seller_os.ps1
```

### 시작은 됐는데 동기화가 실패했을 때

시작 창의 `데이터` 줄이 **확인 필요**면 이 순서로 본다.

```
1. 운영 → 예외 센터        원인 코드를 본다
2. 자격증명 문제면          연동 → 외부 시스템 에서 다시 연결
3. 잠시 뒤 다시             [Seller OS 시작] 을 한 번 더 (따라잡기가 재시도한다)
```

두 번 눌러도 서비스가 두 개 뜨지 않는다. 이미 떠 있으면 그대로 쓴다.

자세한 내용은 `docs/85_local_operation_mode.md`.

### 숫자가 맞는지 확인하고 싶을 때

```
운영 → 검증센터  (/operations/verification)
```

378건을 하나하나 확인하지 않습니다. 시스템이 원천자료(판매처 정산서·수집
기록·장부)와 맞대어 보고, **차이가 있는 것만** 보여줍니다.

화면에서 볼 것은 셋입니다.

```
전체 대사      차이 0인가
마진 신뢰도    실측 몇 건 · 추정 몇 건 · 미확인 몇 건
확인 필요      몇 건인가
```

**"미검증"은 "맞다"가 아닙니다.** 확인할 근거가 아직 없다는 뜻입니다. 환불
손익·입금 확인처럼 원천이 없는 영역은 통과로 표시하지 않습니다.

| 언제 | 무엇을 |
|---|---|
| 월초·월말 | 전체 대사 확인 |
| 정산서를 넣은 뒤 | 정산 금액 차이가 0원인지, 못 붙인 행이 몇 건인지 |
| 숫자가 이상할 때 | 그 주문의 **계산 추적** — 금액마다 출처와 신뢰도가 붙습니다 |
| 코드·정책을 바꾼 뒤 | 기준 사례 회귀 |

**차이가 보여도 자동으로 고치지 않습니다.** 근거를 먼저 보고, 고치는 것은
재계산·정산 재매칭 같은 원래 흐름으로 합니다.

### 기준 사례 — 추천 6건만 확인하면 됩니다

검증센터 아래 **기준 사례**에서 [추천 6건 검토 목록에 담기] 를 누릅니다.
6건은 서로 다른 계산 경로를 하나씩 덮습니다.

```
정산 매칭      실측 수수료로 계산되는 기본 경로
배송비 매출    배송비를 매출로 잡는 결정
판매자 쿠폰    쿠폰을 매출에서 빼는 결정
정책 추정      정산서 없이 추정하는 경로
다중 라인      한 주문번호가 여러 줄인 경우
취소·반품      클레임이 붙은 주문
```

각 건에서 **[원천 확인]** 을 누르면 한 화면에 이만큼이 나옵니다.

```
원천값       금액 · 어디서 나왔는지 · 실측인지 추정인지
             (예: "정산서 파일명 · 시트 · 행 92482554880")
독립 검산     Seller OS 계산기를 쓰지 않고 위 값으로 다시 센 결과
차이         독립 검산 vs Seller OS, 원 단위로
확인할 것     3~5개만
```

**엑셀을 열 필요도, 계산기를 두드릴 필요도 없습니다.** 화면의 값을 보고
[승인] 또는 [보류]만 정하면 됩니다.

| 누를 것 | 뜻 |
|---|---|
| **승인** | 이 값을 앞으로의 기준으로 삼는다 |
| **보류** | 봤지만 지금은 못 정하겠다 (사유 선택) |

> **보류는 오류가 아닙니다.** "확인이 더 필요하다"는 표시일 뿐이고, 회귀
> 검사에서 실패로 세지 않습니다.

> **차이가 0이어도 자동으로 승인되지 않습니다.** 시스템이 현재 계산 결과를
> 기준값으로 채워 주면, 계산이 어떻게 망가지든 늘 통과해서 아무것도 지키지
> 못합니다. 마지막 판단은 사람이 합니다.

승인해도 **판매·정산·마진 데이터는 바뀌지 않습니다.** 기준은 검증용이지
장부가 아닙니다.

자세한 내용은 `docs/86_verification_center.md`, `docs/87_golden_verification_assistant.md`.

### 아침에 여는 화면

```
오늘의 운영  (/operations/daily)
```

맨 위 **"확인 필요"** 만 보면 된다. 아무것도 없으면 그날은 볼 게 없다.

칩을 누르면 해당 묶음만 걸러진 확인 필요 목록으로 간다.

```
주문·클레임    미연결      ← 셀 수 없다는 뜻. "0건 정상" 이 아니다
재고·발주      3건
정산           1건
승인           2건
연동           미연결
```

> 주문과 클레임은 **따로 본다.** NEXT ENGINE 은 둘을 다른 endpoint 로 주고,
> 자동화도 따로 켠다. 둘을 묶어 "정상" 으로 표시하면 주문이 잘 들어오는 동안
> 클레임 수집이 죽어 있어도 알 수 없다 — 그러면 매출이 실제보다 크게 잡힌다.

> **"미연결" 과 "이상 없음" 은 다르다.** 미연결은 확인해 보지 못한 것이다.

### 확인 필요에서 하는 일

| 항목 | 무엇을 하나 |
|---|---|
| 재고 음수 | 0으로 맞추지 말고 **원인을 찾는다.** 대개 기초 재고나 입고 누락 |
| 발주 기한 경과 | 발주 초안을 만들거나 이미 만든 초안을 확정 |
| 재주문 계산 불가 | 소싱처·리드타임을 채운다 (한 번 하면 끝난다) |
| 입고 지연 | 공급처에 확인하거나 예상일을 고친다 |
| 승인 대기 | 원가·가격 변경 요청을 보고 승인/거절 |
| 정산 미매칭 | 판매처 정산서와 주문을 맞춘다 |

### ★ 주문 입력

주문이 장부에 들어오는 길은 **두 개이고 역할이 다르다.**

```
Excel 가져오기        초기 구축 · 복구 · 백필      (평상시 업무가 아니다)
NEXT ENGINE 주문 API  2026-07-26 이후 상시 수집원   (자동)
```

지금 장부에 있는 374건은 **초기 구축 데이터**다. 매일 엑셀을 내려받아야 하는
구조가 아니다. 그렇게 오해하면 커넥터가 붙은 뒤에도 같은 일을 계속하게 되고,
같은 주문이 두 경로로 들어와 매출이 겹친다.

```
판매장부 → 가져오기        ← Excel. 초기/복구용으로만 쓴다.
```

#### NEXT ENGINE 주문 자동 동기화

```
읽기 검증        완료
스토어 연결      완료 (11번가 · 스마트스토어 · 쿠팡)
상품 연결        완료 (미연결 1건은 보류 — 아래 참조)
실행 방식        자동. 설정 → 자동화 → 주문 자동 수집
클레임(취소/반품) 별도 자동화로 수집한다 (바로 아래)
```

**설정하는 곳**

```
설정 → 자동화 → 주문 자동 수집
  사용 = 켬 / 모드 = 자동 실행
  실행 주기        몇 분마다 확인할지
  겹쳐 읽을 일수    최근 며칠을 매번 다시 읽을지 (최대 10일)
```

겹쳐 읽는 이유가 있다. NEXT ENGINE 은 "언제 수정됐는지" 를 주지 않는다.
새로 생긴 것만 읽으면 **이미 받은 주문이 나중에 바뀌어도 영원히 모른다.**
그래서 매번 최근 구간을 통째로 다시 읽는다. 다시 읽어도 같은 주문이 두 번
들어오지는 않는다.

**지금 상태 보는 곳**

같은 화면 아래 `주문 동기화 상태` 에 계정별로 나온다.

```
마지막 시도    마지막으로 판매처를 부른 시각
마지막 성공    마지막으로 **끝까지** 성공한 시각
결과          성공 / 일부만 처리 / 실패 + 사유
최근 건수      조회 · 신규
```

둘을 따로 보는 이유는 하나다. 합쳐 놓으면 몇 시간째 못 읽고 있는 상태가
지난 성공 시각 뒤에 숨는다. **마지막 성공이 오래됐으면 지금 안 들어오고
있는 것이다.**

[지금 동기화] 로 즉시 실행할 수도 있다. 자동 실행이 돌고 있으면 겹치지 않고
`이미 실행 중` 으로 끝난다.

**연결 안 된 상품이 있으면**

그 주문만 보류되고 나머지는 정상으로 들어온다. 이름이 비슷하다고 자동으로
잇지 않는다 — 잘못 붙은 매출은 나중에 마진이 이상해질 때야 드러나고, 그때는
어느 주문이 잘못됐는지 되짚을 수 없다.

보류된 것은 `예외 센터 → 연동` 에 뜬다. 상품을 연결하면 **다음 동기화가 그
주문이 있던 기간을 겨냥해 다시 읽어 되살린다.** 자동 동기화는 최근 며칠만
보기 때문에, 되살리기가 없으면 오래된 보류 주문은 영영 안 들어온다.

> 매핑을 저장했다고 경고가 바로 사라지지는 않는다. **실제로 그 주문이 장부에
> 들어온 뒤에** 닫힌다. 경고가 남아 있으면 아직 복구가 안 된 것이다.

cutover(2026-07-26) **이전** 주문은 API 가 건드리지 않는다. 그 구간은 Excel 로
넣은 확정 데이터다. 자동 동기화도 그 아래로는 내려가지 않는다.

**장애가 났을 때**

```
인증 실패        자격증명을 다시 등록해야 한다. 그때까지 주문이 안 들어온다
요청 한도 초과    다음 주기에 저절로 다시 시도한다. 할 일 없음
응답 형식 변경    판매처가 바뀌었다. 잘못된 주문을 만들지 않고 멈춘 것이다
건수 대사 실패    읽은 수와 처리한 수가 안 맞는다. 성공으로 기록하지 않는다
```

전부 `예외 센터 → 연동` 에 사유까지 나온다. 실패한 실행은 **마지막 성공을
앞으로 옮기지 않는다.**

#### NEXT ENGINE 취소·반품 자동 수집

```
설정 → 자동화 → 취소·반품 자동 수집
```

**이 기능은 반품 업무를 대신하지 않는다.** 취소 승인도, 회수 지시도, 교환
처리도 하지 않는다. 판매처에서 이미 일어난 일을 **읽어서 매출을 맞추는 것**
뿐이다. 반품 처리는 그대로 판매처에서 한다.

```
사용 = 켬 / 모드 = 자동 실행
실행 주기            몇 분마다 확인할지
클레임 조회 기간     며칠 전 주문까지 되돌아볼지 (1~180일)
```

**주문의 "겹쳐 읽을 일수" 와 뜻이 다르다.** 판매처가 클레임을 날짜로 찾을 때
쓰는 날짜가 클레임 날짜가 아니라 **원 주문 날짜**다. 그래서 "최근 3일" 로
두면 3일 안에 주문된 것의 취소만 보이고, 오늘 들어온 6월 주문의 반품은
영영 안 보인다. 이 값은 **반품이 아직 들어올 수 있는 주문 기간**으로 잡는다.

> 넓게 잡을수록 비싸다. 판매처가 상태별로만 조회를 받아 줘서, 창 하나당
> 요청이 17번이다. 90일이면 한 번 돌 때 150번 넘게 부른다. 실제 반품 가능
> 기간보다 넉넉하게만 잡고 그 이상 늘리지 않는다.

**무엇이 장부에 반영되나**

```
취소완료 · 반품완료      매출이 줄어든다        조정 행이 생긴다
취소요청 · 반품수거중    아직 아니다            확정되면 그때 반영된다
교환                    매출이 안 바뀐다        아무 일도 하지 않는다
철회                    앞서 줄인 만큼 되돌린다  앞 기록을 지우지 않는다
```

원 주문은 **고치지 않는다.** 3만원 주문을 0원으로 바꾸는 게 아니라 -3만원
조정을 하나 더 쌓는다. 그래야 "그때 3만원 주문이 있었고 나중에 취소됐다" 는
두 사실이 다 남는다.

이미 마감한 달의 주문이 지금 반품되면 **그 달을 다시 열지 않는다.** 지금
열린 달에 조정을 단다. 나중에 "왜 8월 매출에 7월 주문이 있나" 를 물으면
조정 행에 두 달이 다 적혀 있다.

**재고와 원가는 자동으로 되돌리지 않는다.** 반품완료가 곧 물건이 창고에
돌아왔다는 뜻이 아니다 — 미발송·파손·폐기가 전부 같은 상태로 온다. 실물
입고는 사람이 확인한다.

같은 이유로 **순이익은 아직 확정되지 않는다.** 매출이 얼마나 줄었는지는 알
수 있지만, 반품 수수료가 얼마나 환급되는지는 판매처 정산서에만 있다.

**확인이 필요할 때**

`예외 센터 → 연동` 에 뜬다. 네 가지이고 급한 정도가 다르다.

| 뜨는 것 | 뜻 | 마감 |
|---|---|---|
| 매출 반영을 못 한 취소·반품 | 확정됐는데 금액을 모른다. **매출이 아직 안 줄었다** | **막는다** |
| 어느 주문 라인인지 모르는 취소·반품 | 한 주문번호에 상품이 여럿이다 | **막는다** |
| 원 주문을 못 찾은 취소·반품 | 그 주문이 장부에 없다 | 막지 않는다 |
| 해석할 수 없는 클레임 상태 | 판매처가 모르는 코드를 보냈다 | **막는다** |

세 번째만 마감을 막지 않는다. **되돌릴 매출이 애초에 없기 때문이다** —
출고 전에 취소돼서 판매로 잡힌 적이 없는 건이면 장부 금액은 정확하다.
실제로 지금 14건이 이 상태이고 전부 정상으로 확인됐다.

그래도 목록에 남겨 두는 이유는, 주문 동기화가 밀려서 아직 안 들어온 경우와
구분이 안 되기 때문이다. 주문이 뒤늦게 들어오면 **다음 동기화가 자동으로
이어 붙이고 그때 매출 조정을 만든다.** 주문 쪽과 같이, 매핑만 생겼다고
경고가 닫히지 않는다 — 실제로 매출에 반영된 뒤에 닫힌다.

나머지 셋은 마감을 막는다. 그 상태로 달을 잠그면 순매출이 실제보다 크게
잡힌 채로 확정되고, 그 위에서 순이익과 파트너 배분이 전부 계산된다.

**마감 화면에 조정 금액이 한 줄 더 뜬다.**

```
이 달 확정 매출에 반영되지 않은 취소·반품 조정 -24,000원이 있습니다.
```

확정 스냅샷의 총매출은 **주문만 더한 값**이라 취소·반품 조정이 들어 있지
않습니다. 사업비용 정정(`expense_adjustment`)도 지금 같은 방식이고, 조정을
순이익·배분에 반영할지는 **아직 정해지지 않았습니다.** 마감을 막지는 않으니
금액을 확인하고 잠가 주세요 — 정하고 나면 그때 계산에 넣습니다.

> **경고를 "무시" 해도 데이터 복구는 계속된다.** 경고를 그만 보는 것과
> 매출을 버리는 것은 다른 결정이다.

## 2. 재고가 필요할 때

### 지금 몇 개 있나

```
재고·재주문  (/inventory)
```

행을 누르면 **원장**이 펼쳐진다 — 재고가 왜 지금 숫자인지 한 줄씩 보인다.

```
예약        주문 연동 안 됨   ← 미출고 주문을 모른다. 0 이 아니다
판매가능    계산 불가        ← 예약을 모르니 계산할 수 없다
```

### 실사하고 맞추기

행을 펼쳐 **재고 조정**. 목표 수량이 아니라 **차이**를 넣는다.

```
장부 12개, 실제 세어 보니 9개  →  감소 3, 사유 "실사 차이"
```

사유는 필수다. 몇 달 뒤에 왜 숫자가 바뀌었는지 알아야 하기 때문이다.

> 음수가 되어도 막지 않는다. 0으로 만들면 몇 개가 빈 것인지 영영 모른다.

이미 처리 안 된 초안이 있으면 버튼 대신 «기존 초안 보기» 가 뜬다(중복 발주 방지).

```
발주 → [발주 초안 만들기]
```

공급처를 고르고 품목을 검색해 담는다. 단가를 모르면 **비워 두지 말고 확인한다** —
0원으로 만들면 그게 그대로 취득원가가 된다.

```
DRAFT       아직 아무 데도 안 나갔다
  ↓ [발주 확정]        ← 여기서 돈을 쓰기로 결정한다
ORDERED
  ↓ [입고 처리]        ← 온 만큼만 적는다
PARTIALLY_RECEIVED / RECEIVED
```

입고하면 재고가 그만큼 늘어난다. **취득원가는 발주 단가로 박제된다** — 나중에
소싱 원가가 올라도 이미 들어온 재고의 원가는 안 바뀐다.

부분 입고는 여러 번 할 수 있다. 같은 화면에서 두 번 눌러도 재고가 두 번 늘지
않는다.

> Seller OS 는 **공급처에 주문을 보내지 않는다.** 실제 주문은 사람이 공급처
> 사이트에서 한다. 여기서 하는 것은 "무엇을 얼마에 주문했고 얼마나 들어왔나" 의
> 기록이다.

## 4. 매월 — 마감

```
1. 사업비용 입력 · 증빙 첨부       (/expenses)
2. 판매처 정산서 가져오기 · 대사   (/settlements/marketplace)
3. 월 마감                        (/settlements/monthly)
4. 수익배분 확인                  (/settlements/distribution)
5. 지급 기록                      (/payouts)
6. 세무사 리포트 내보내기          (/reports)
```

마감 전에 **확인 필요**를 비워 두는 것이 좋다. 마감을 막는 항목은 `BLOCKING`
으로 표시된다.

> 마감한 달은 나중에 값이 바뀌어도 **다시 계산되지 않는다.** 그게 마감의 뜻이다.
> 늦게 도착한 정산·클레임은 열린 달에서 조정한다.

### 정산 대사 — 쿠팡 정산서 파일로 합니다

쿠팡 API 는 아직 막혀 있다(IP 미등록). 대신 **WING 에서 받은 엑셀**을 올린다.

```
쿠팡 WING > 정산 > 매출·정산 상세 엑셀 다운로드
        ↓
/settlements/marketplace/import
        ↓
스토어 선택 → 미리보기 → 확인하고 반영
```

**미리보기가 먼저다.** 무엇이 들어갈지 보고 반영한다. 같은 파일을 여러 번
올려도 정산 행이 두 번 생기지 않는다.

대사 결과는 셋으로 갈린다. **각각 할 일이 다르다.**

```
자동 매칭        (판매처, 주문번호)로 주문이 딱 하나 — 끝난 것이다
모호            그 주문에 상품 라인이 여럿 — 정산 화면에서 직접 고른다
                (고르는 것은 승인 대상이다. 손익 귀속이 바뀐다)
주문 못 찾음     그 번호의 판매가 장부에 없다. 주문이 늦게 들어왔거나,
                광고비·보증금처럼 주문과 무관한 행이면 사유와 함께 제외한다
```

**금액이나 날짜가 비슷하다고 자동으로 붙이지 않는다.** 틀린 매칭은 틀린
손익이 되고, 잘못 붙은 매칭은 나중에 봐도 알아채기 어렵다.

#### 알아 둘 것

- 정산서 한 파일 = **한 정산 회차**다. `(1)` `(2)` 가 붙은 파일은 중복이
  아니라 다른 회차일 수 있으니 전부 올린다.
- 주문 하나가 정산서에서 **행 셋**으로 온다(상품 · 기본배송료 · 추가배송료).
  행 수가 주문 수의 3배로 보이는 것이 정상이다.
- 파일이 주는 날짜는 **정산예정일**이다. 입금됐다는 뜻이 아니다 — 현금흐름에
  입금이 자동으로 잡히지 않는다.
- 이미 넣은 행의 금액이 달라진 정산서를 올리면 **덮어쓰지 않고 알려 준다.**
  재발행이면 정정으로 처리해야 한다.

#### 정산서를 넣은 뒤 — 재계산을 해야 숫자가 바뀝니다

정산서를 넣는다고 실 마진이 바로 바뀌지 않는다. **그 달이 "재계산 필요" 로
표시**되고, 재계산을 실행해야 반영된다.

```
정산서 가져오기 → 월별 정산 화면에 "재계산 필요" → [다시 계산] → 실 마진 갱신
```

적재가 과거 손익을 조용히 덮지 않기 위해서다. 재계산 전에는 마감이 막힌다
(낡은 숫자로 확정하지 않게).

**무엇이 달라지나** — 정산서가 붙은 주문만 바뀐다.

```
매출     상품매출 + 배송비매출 - 판매자 부담 쿠폰   ← 정산서 실제 금액
수수료   판매처가 실제로 뗀 금액 (VAT 포함)         ← 정책 요율 추정 대신
```

정산서가 안 붙은 주문은 그대로 장부 + 정책 추정을 쓴다.

> 판매처 정산서에는 광고비·반품비가 없다. 그 항목들은 **장부 값을 그대로
> 쓴다** — 정산서에 없다고 0 으로 지우지 않는다.

**"정산서와 장부 금액이 다릅니다" 가 뜨면**

판매 원본은 자동으로 고치지 않는다. 대개 장부의 수량이나 배송비매출이 빠진
경우다 — 판매 장부에서 확인하면 된다. 실 마진은 정산서 금액으로 계산된다.

> 순이익·파트너 배분은 실 마진을 통해 달라진다. 다만 **취소·반품 조정과
> 사업비용 정정, 정산 정정 세 가지는 아직 순이익에 접지 않는다** — 셋을 함께
> 정해야 하는 문제로 남아 있다(docs/83 §8).

> 미확정 스냅샷(`UNCONFIRMED_SNAPSHOT_…`)은 정산서가 아니다. 올리면 거부된다.

확정한 정산 건을 나중에 고칠 때는 **원본을 수정하지 않고** 열린 달에 정정을
만든다 — 사업비용 정정과 같은 방식이다.

### 세무 리포트

`종합소득세참고`·`사업소득` 두 가지는 **아직 제공하지 않는다.** 목록에는 보이되
"제공 안 함" 으로 표시된다 — 빈 파일을 받아 세무사에게 넘기는 것이 더 위험하기
때문이다.

### 마스터 키

자격증명은 DB 에 암호문으로, 키는 환경변수에 있다. **둘을 같은 곳에 백업하지
않는다.** 키를 잃으면 DB 를 되살려도 외부 연동 자격증명은 못 푼다(판매·비용
데이터는 무사하다).

키는 비밀번호 관리자 같은 **다른 곳**에 따로 보관한다.

### 시스템 상태

```
운영 → 시스템 상태
```

worker 가 멈췄는지 본다. 실패가 쌓이면 알림이 온다.

## 6. 권한

| 역할 | 재고 수량 | 취득원가 | 발주 | 재고 조정 |
|---|---|---|---|---|
| ADMIN | ✅ | ✅ | ✅ | ✅ |
| OPERATOR | ✅ | ✅ | ✅ | ✅ |
| SOURCING | ✅ | ✅ | 초안 생성 | ❌ |
| ACCOUNTING | ✅ | ✅ | 조회 | ❌ |
| READONLY | ✅ | ❌ | ❌ | ❌ |
| EXTERNAL_ACCOUNTANT | ❌ | ❌ | ❌ | ❌ |

**재고 수량과 원가는 다른 권한이다.** 몇 개 남았는지는 운영 정보고, 얼마에
샀는지는 사업의 핵심 정보다. 조회 전용 계정은 수량만 본다.

## 7. 자주 겪는 상황

### "재주문이 아무것도 안 나온다"

셋 중 하나다.

1. **기준을 안 정했다** → 설정 → 자동화 → 재주문 감시
2. **소싱처가 없다** → 소싱 연결 가져오기 (가장 흔하다)
3. **아직 여유가 있다** → 정상이다

`/inventory` 의 "추천 불가" 목록이 이유를 알려준다.

### "마진이 100% 로 나온다"

원가가 없는 상품이다. 지금은 그런 상품의 마진을 **"확인 불가"** 로 표시한다 —
예전에는 원가 0원으로 계산해 100% 로 보였다.

상품 원가를 채우거나, 판매 기록에 매입가를 넣는다.

### "예약 수량이 0 인가?"

아니다. **모르는 것**이다. 미출고 주문을 알려면 판매처 주문 API 가 필요하다.

### "알림이 안 온다"

일일 리포트 자동화가 꺼져 있거나, 받는 역할이 아니다(READONLY 는 안 받는다).

### "발주를 눌렀는데 공급처에 주문이 안 갔다"

정상이다. Seller OS 는 외부에 주문을 보내지 않는다. 실제 주문은 공급처
사이트에서 하고, 여기에는 기록만 남긴다.

## 8. 하지 말아야 할 것

| | 왜 |
|---|---|
| 재고를 목표 수량으로 덮어쓰기 | 원장이 어긋나고 누가 언제 바꿨는지 못 찾는다 |
| 손으로 `alembic downgrade` | 대상 DB 를 착각하면 데이터가 날아간다. `verify_migrations` 를 쓴다 |
| 백업 파일을 저장소에 커밋 | 사업 데이터 전체와 자격증명 암호문이 들어 있다 |
| 마스터 키를 DB 백업과 같은 곳에 | 백업 하나가 새면 전부 풀린다 |
| 리드타임·MOQ 를 모르는데 채우기 | 그 숫자로 발주 시점이 계산된다 |
| 쿠팡 API 키 재발급 | 넥스트엔진 연동이 끊긴다. 자체개발용으로 **별도 발급** |
