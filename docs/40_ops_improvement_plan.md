## 1. 먼저 짚어야 할 것 — "없는 기능"이 아니라 버그인 6건

기획에 앞서 코드·DB를 직접 확인한 결과다. 전부 [Confirmed] — 파일과 라인을 특정했다.

### B-01. 팝업·드로어가 전부 투명하다 🔴 최우선

- **증상**: 사용자 표현 "팝업 띄우는 거 투명을 넣어놔서 잘 안 보여"
- **원인**: Tailwind v4는 `@theme` 블록의 **`--color-*` 네임스페이스**에서만 유틸리티를 생성한다.
  `frontend/app/globals.css:81` 은 `--popover` / `--popover-foreground` 로 선언되어 있어
  `bg-popover`, `text-popover-foreground` 유틸리티가 **아예 생성되지 않는다**.
  클래스는 조용히 무시되고 배경이 없는 채로 렌더된다.
- **영향 범위**: `bg-popover` 9곳, `text-popover-foreground` 7곳 —
  `dialog.tsx`, `sheet.tsx`, `popover.tsx`, `dropdown-menu.tsx`, `select.tsx`, `command.tsx`, `tooltip.tsx`.
  **⌘K 검색 팔레트와 상품 수정 드로어를 포함한 모든 오버레이가 투명**하다.
- **부수 원인**: `dialog.tsx:42` 오버레이가 `bg-black/10` 으로 과하게 옅다.
- **수정**: `@theme` 에 `--color-popover` / `--color-popover-foreground` 추가 (2줄), 오버레이 `bg-black/40`.
- **의미**: 이것 때문에 **R-04(상품 수정 창을 오른쪽에서 나오게)는 이미 구현되어 있는데도 없는 것처럼 보였다.**
  `products/page.tsx` 는 이미 `Sheet`(기본 `side="right"`)를 쓴다.

### B-02. 대시보드 위젯 3개가 BE 응답과 필드명이 다르다 🔴

| 위젯 | BE 반환 | FE 기대 | 결과 |
|---|---|---|---|
| 월별 추세 차트 | `year_month`, `revenue`, `actual_margin` | `month`, `revenue`, `margin` | **X축 라벨 없음 + 마진 선 아예 안 그려짐** |
| 마진 격차 TOP 10 | `expected_margin_rate`, `actual_margin_rate`, `delta_rate` | `target_rate`, `actual_rate`, `gap` | **3개 컬럼 전부 NaN%** |
| 마진하락 경고 | `{"alerts": [...]}` | `alertData.items` | **항상 "경고 없음"** |

근거: `backend/app/api/v1/reports.py:354-443` vs `frontend/app/(app)/dashboard/page.tsx:15-26, 196-249`

→ 사용자의 "그래프가 좀 더 눈에 띄었으면" 은 **미적 요구 이전에 절반이 안 그려지고 있는 상태**다.

### B-03. 옵션/Variant 목록의 상품명이 빈칸 🟠

- `frontend/app/(app)/products/options/page.tsx:34` → `accessorKey: "name"`
- 실제 API 필드 → `name_ko` (`lib/api/products.ts:9`, DB 컬럼도 `name_ko`)
- 사용자 표현 "상품 옵션도 상품명이 제대로 들어오지 않았고" **정확히 이것**. 1줄 수정.

### B-04. 비용 카테고리 화면이 존재하지 않는 API를 부른다 🔴

- FE는 `/expense-categories` (CRUD 4종)를 호출한다 (`lib/api/categories.ts`).
- **BE에 해당 라우터가 없다.** 카테고리는 `/policies/expense_category` 로 관리된다
  (`api/v1/policies.py` — 11개 정책 kind 중 하나).
- 게다가 FE 폼은 `code`, `parent_id`, `is_deductible` 을 보내는데
  `expense_category_policy` 테이블에는 **`code` / `parent_id` 컬럼이 자체가 없다**
  (실제 컬럼: `name`, `kind`, `default_tax_deductible`, `default_settlement_deductible`, `sort_order`).
- → R-13(비용 카테고리)은 "개선"이 아니라 **정상화**가 먼저다.

### B-05. 사업비용 목록에 키워드 검색이 BE에도 없다 🟡

- `list_expenses` 필터: `from_dt`, `to_dt`, `category_id`, `evidence_status` 뿐 (`services/expense.py:121`).
- 기간 필터는 이미 있다 → R-12의 "기간 검색"은 **FE 노출만 손보면 되고**, 키워드는 BE 추가 필요.

### B-06. 판매장부 키워드 검색은 BE에 이미 있는데 FE에 입력창이 없다 🟡

- `list_sales(q=...)` 지원 + 라우터 `q` 파라미터 존재 (`services/sales.py:55,74`, `api/v1/sales.py:45`).
- FE `sales/page.tsx` 에는 검색 입력이 없다. **R-09는 FE 입력창 추가만으로 대부분 해결.**
- 단, 판매장부 `q` 는 옛날 방식(`%q%` 단일 매칭)이라 `쿨링 스카프` 처럼 띄어쓰기가 섞이면 실패한다.
  PR #11에서 만든 `services/search.py` 의 토큰 AND 규칙으로 통일해야 한다.

### R-01. 대시보드 — 눈에 띄는 그래프 + 기간 설정

**현황**
- KPI 카드 6개 + AreaChart 1개 + 하단 위젯 2개. 그중 3개가 B-02로 깨져 있음.
- `GET /reports/dashboard-summary` 는 **파라미터가 없다.** `date.today()` 하드코딩 (`reports.py:278`).
  기간을 바꿀 방법이 코드상 존재하지 않음.
- `/reports/category-margin` 은 호출만 하고 렌더링 안 함 (`dashboard/page.tsx:75` `_categoryData`).

**기획 결정**

1. **기간 컨트롤을 대시보드 최상단에 전역 배치.** 프리셋 + 커스텀:
   `이번 달 / 지난 달 / 최근 3개월 / 최근 6개월 / 올해 / 직접 지정(월~월)`
   - 선택값은 URL 쿼리(`?from=2026-03&to=2026-08`)에 반영 → 새로고침·공유 시 유지.
   - **모든 대시보드 위젯이 같은 기간을 공유**한다 (위젯별 개별 기간 금지 — 숫자 비교가 불가능해짐).
2. **비교 기준**은 "직전 동일 길이 기간"으로 통일. 3개월 선택 시 그 직전 3개월과 비교.
3. **차트 3종으로 확장** (기존 1종):
   - ① 월별 매출/마진 **복합 차트** — 매출은 막대, 마진율은 꺾은선(우측 축). 현재는 둘 다 면적이라 겹쳐서 안 읽힘.
   - ② 판매처별 매출 비중 — **가로 막대**. (도넛은 5개 넘어가면 판독 불가 → 막대 채택)
   - ③ 비용 구성 — 원가/마켓수수료/광고비/사업비용 **누적 막대**. "돈이 어디로 새는가"를 한 화면에.
   - `/reports/category-margin` 을 ②에 연결해 죽은 쿼리를 살린다.
4. **가독성 규칙** (Designer 위임 사항):
   - 금액 축은 만원/백만원 단위 축약(`1,250만`), 툴팁에서만 원 단위 전체 표기.
   - 데이터 0건 구간은 선을 끊고 "데이터 없음" 배지 — 0으로 이어 그리면 매출이 급락한 것처럼 보인다.
   - 색은 `디자인.md` 토큰 고정: 매출 `--color-accent`(#4F46E5), 마진 `--color-success`, 비용 `--color-warning`.

### R-02. 알림센터 — 기능이 뭔지 모르겠다 + 메신저 연동

**현황**
- 알림 종류 7종이 DB에 이미 정의: `SETTLEMENT_DEADLINE`(정산 마감), `VAT_DEADLINE`(부가세 신고),
  `MARGIN_DROP`(마진 하락), `STOCKOUT_RISK`(품절 위험), `POLICY_REVIEW`(정책 재검토),
  `ACCOUNTANT_COMMENT`(세무사 코멘트), `SYSTEM`.
- 채널 enum에 **`KAKAO`, `SLACK`, `TELEGRAM`, `WEBHOOK` 이 이미 있다.** 없는 건 `DISCORD` 하나.
- 어댑터 레지스트리 구조가 이미 플러그인식 (`core/notification/registry.py`) — EMAIL / IN_APP 만 구현됨.
- 채널 활성화는 `FEATURE_NOTIFICATION_<CODE>` 환경변수 플래그로 게이트되어 있음.

→ **"기능이 뭔지 모르겠다"의 원인은 기능 부재가 아니라, 화면이 "무엇을 언제 알려주는지" 설명하지 않기 때문.**
현재 알림센터는 수신함일 뿐이고, 발송 규칙을 보여주는 곳이 없다.

**기획 결정**

1. **알림센터를 2탭으로 재구성**
   - **[받은 알림]** — 기존 목록. + 종류별 필터, 기간 필터.
   - **[알림 규칙]** — *신규.* 7종을 카드로 나열하고 각각에 대해
     `무엇을 / 언제 / 어떤 조건에서 / 어느 채널로` 를 **평문 한국어로** 명시하고 on/off + 채널 선택.
     예: `정산 마감 — 매월 5일 09:00, 전월 정산이 CONFIRMED 아니면 → 이메일 + Discord`
2. **메신저 채널 3종 추가**: `DISCORD`(신규 enum), `SLACK`, `KAKAO`.
   - **Discord / Slack** = Incoming Webhook 방식. URL 1개만 등록하면 끝. **가장 먼저 구현.**
   - **KAKAO** = 카카오 알림톡. 사업자 등록 + 발신프로필 + 템플릿 사전심사가 필요해
     **셀프 서비스로 즉시 붙일 수 없다.** [Confirmed: 카카오 비즈메시지 정책상 템플릿 사전승인 필수]
     → **MVP에서는 "카카오톡 나에게 보내기"(memo API) 또는 알림톡 대행사(솔라피 등) 중 택1**.
     이건 계정 준비가 선행되어야 하므로 **Phase 7로 미루고, 어댑터 인터페이스만 열어둔다.**
   - 텔레그램은 봇 토큰만으로 즉시 되므로 Discord/Slack과 같이 묶어 처리 (추가 비용 0).
3. **🔒 보안 결정 (중요)**: Webhook URL은 **그 자체가 자격증명**이다. URL을 아는 사람은 누구나
   그 채널에 글을 쓸 수 있다. CLAUDE.md Security Rules("평문 저장 금지")와 충돌한다.
   - **[결정 D-291]** webhook URL은 `password_vault_entry`(보관위치만 저장)에 **넣지 않는다**.
     신규 `notification_channel_config` 테이블에 **애플리케이션 레벨 암호화(Fernet/AES-GCM)** 로 저장하고,
     키는 `.env` 의 `SECRET_ENCRYPTION_KEY` 로 관리한다.
   - 조회 API는 **항상 마스킹**해서 반환 (`https://discord.com/api/webhooks/…/****`). 원문은 절대 GET으로 안 나간다.
   - 감사 로그에 등록/변경/삭제를 남긴다. 로그 본문에 URL을 쓰지 않는다.
4. **알림 발송은 실패해도 본 업무를 막지 않는다.** 발송 실패는 `notification.delivery_status='FAILED'` +
   `error_message` 기록 후 조용히 넘어간다. 재시도는 최대 3회 지수 백오프.
5. **테스트 발송 버튼** 필수 — 등록 직후 "테스트 전송" 으로 즉시 검증되지 않으면 아무도 안 쓴다.

**AC**
- [ ] 알림 규칙 탭에서 7종 각각의 발동 조건이 한국어 문장으로 보인다
- [ ] Discord/Slack Webhook URL 등록 → "테스트 전송" → 실제 채널에 메시지 도착
- [ ] 등록된 URL은 목록·상세·API 응답 어디에서도 원문이 노출되지 않는다
- [ ] 채널 1개가 실패해도 나머지 채널과 IN_APP 알림은 정상 발송
- [ ] 종류별/기간별 필터로 받은 알림을 조회할 수 있다

### R-03. 계정 설정 — 직급 등 다양한 정보

**현황**
- `app_user` 컬럼: `email`, `password_hash`, `display_name`, `role`, `is_active`, `last_login_at`, 초대 관련.
- `/me` 화면은 표시이름 변경 + 비밀번호 변경뿐 (`me/page.tsx`).
- `role`(ADMIN/OPERATOR/SOURCING/ACCOUNTING/READONLY/EXTERNAL_ACCOUNTANT)은 **권한**이지 직급이 아니다.

**기획 결정**

**권한(role)과 직급(job_title)을 분리한다.** 섞으면 "부장인데 읽기전용" 같은 조합을 표현할 수 없다.

`app_user` 확장 컬럼:

| 컬럼 | 용도 | 비고 |
|---|---|---|
| `job_title` | 직급/직책 (대표, 팀장, 매니저, 사원 …) | 자유 텍스트. enum 금지 — 조직마다 체계가 다름 |
| `department` | 부서 | 자유 텍스트 |
| `employee_no` | 사번 | 선택 |
| `phone` | 연락처 | 알림 채널 연동에 사용 |
| `joined_at` | 입사/합류일 | 수익배분 시뮬레이터(R-10)에서 참여 시작 시점으로 사용 |
| `avatar_url` | 프로필 이미지 | 선택 |
| `timezone` / `locale` | 개인 설정 | 기본값은 org 설정 상속 |
| `linked_partner_id` | 수익배분 파트너와 연결 | `partner.linked_user_id` 의 역참조 (이미 존재) |

**제외 결정**: 주민등록번호·계좌번호·주소는 **저장하지 않는다** (CLAUDE.md Security Rules).

### R-07 + R-08. 등록가 시뮬레이션 & 마진계산기 통합 + 세금 고도화 🔴 핵심

두 항목은 같은 계산 엔진을 쓰므로 함께 기획한다.

**현황**
- `/margin/simulator` (등록가 역산) 와 `/margin/calculator` (마진 정산) 가 **별도 메뉴, 별도 사이드바 그룹**.
  실제로는 같은 식의 방향만 다르다: `원가 → 가격` vs `가격 → 마진`.
- 시뮬레이터 입력은 4개(마진타입/판매처/원가/결제수단)뿐. 수수료율이 화면에 안 보인다.
- **부가세 계산이 실제 세법과 다르다** (`services/calculation.py:107-112, 166-167`):
  ```python
  vat = (sale_price - marketplace_fee) * vat_rate   # ← 현재
  ```
  코드 주석에도 `세무사 검토 필요` 라고 적혀 있다.
- `tax_policy.calculation_method` 에 `STANDARD_RATIO / SIMPLE_DEEMED / EXEMPT / OVERSEAS_ZERO_RATED` 가
  **정의되어 있고 DB에서 읽어오지만, 계산 코드에서 한 번도 분기하지 않는다.**
  즉 **간이과세자를 선택해도 일반과세자와 똑같이 계산된다.**
- 현재 seed 는 `GENERAL` 1건뿐, `business_type` 은 NULL.

→ 사용자의 "너무 단순한 계산인 듯" 은 **정확한 지적이며, 실제로 틀린 계산이다.**

#### 7-1. 부가세 계산 재설계 (리서치 노트)

> ⚠️ **아래 세율·비율은 전부 `tax_policy` 테이블 값으로 관리한다. 코드에 상수로 넣지 않는다.**
> (CLAUDE.md Generalization Principle)
> 세법은 자주 바뀌므로 **수치는 세무사 확인 후 정책 테이블에 입력**한다. 아래는 구조 설계용 기준값이다.

**일반과세자 (STANDARD_RATIO)**

```
매출세액 = 공급가액 × 10%
  └ 판매가가 소비자가(VAT 포함)이면  매출세액 = 판매가 × 10/110
매입세액 = 공제 가능한 매입의 부가세 합
  └ 국내 매입 원가, 마켓 수수료, 광고비, 택배비 중 세금계산서/카드전표를 받은 건
납부세액 = 매출세액 − 매입세액
```

현재 코드의 두 가지 오류:
1. `sale_price × 10%` — 판매가가 VAT 포함이면 `×10/110` 이어야 한다. **약 10% 과대계상.**
2. 마켓 수수료를 **과세표준에서 차감**하고 있다. 실제로는 수수료의 부가세를
   **매입세액으로 공제**하는 구조다. 결과값이 우연히 비슷해 보여도 논리가 다르고,
   수수료에 세금계산서가 없으면 공제가 안 되므로 **틀린 답이 나온다.**

**간이과세자 (SIMPLE_DEEMED)**

```
납부세액 = 공급대가 × 업종별 부가가치율 × 10%
매입세액공제 = 매입액(공급대가) × 0.5%
납부의무 면제: 해당 과세기간 공급대가가 기준금액 미만이면 납부 면제
```
- 업종별 부가가치율: 소매업/전자상거래 소매업 **15%** 적용 [Uncertain — 업종 판정과 최신 비율은 세무사 확인 필요]
- 간이과세 적용 기준(직전연도 공급대가 한도)과 납부의무 면제 기준금액은
  **최근 몇 년 사이 여러 번 상향되었다.** 내 지식으로 확정하지 않는다.
  → **`tax_policy` 에 입력 필드로 두고, 초기값은 세무사 확인 후 채운다.**
- 간이과세자는 매입세액 공제가 사실상 거의 없다 → **같은 매출·같은 원가라도 일반과세자보다 마진이 다르게 나온다.**
  이 차이를 화면에서 보여주는 것이 이 기능의 핵심 가치다.

**면세 (EXEMPT)** — 부가세 0. **해외직구/수출 영세율 (OVERSEAS_ZERO_RATED)** — 매출세액 0, 매입세액은 공제.

#### 7-2. 마켓 수수료의 부가세 처리 (신규 발견 이슈)

`marketplace_fee_policy` 에 **수수료율이 VAT 포함인지 별도인지 구분하는 필드가 없다.**
마켓마다 다르다 — 쿠팡은 일반적으로 VAT 별도 표기, 일부 마켓은 포함 표기.
이게 틀리면 수수료 자체가 10% 어긋난다.
→ **`marketplace_fee_policy.fee_vat_included BOOLEAN` 추가** (기본값은 마켓별 확인 후 지정).

#### 7-3. 통합 설계

**[결정 D-292] 계산 엔진은 하나, 진입점은 3개.**

| 진입점 | 위치 | 방향 | 목적 |
|---|---|---|---|
| ① 상품 등록/수정 인라인 | 상품 드로어 `원가·마진` 탭 | 양방향 | **주 사용처.** 등록하면서 바로 마진 확인 → 저장 시 반영 |
| ② 등록가 시뮬레이터 | `/margin/simulator` | 원가 → 가격 | 목표 마진율별 권장가 |
| ③ 마진 계산기 (번외) | `/margin/calculator` | 가격 → 마진 | 상품 등록 없이 빠른 계산 |

- 사용자 제안대로 **①이 주력, ③은 "번외"** 로 위상을 낮춘다.
  사이드바에서 `마진 계산기`를 `Profit` 그룹 → **`도구` 그룹**으로 이동.
- ②③는 **같은 컴포넌트의 모드 전환**으로 구현하고 한 페이지로 합친다
  (`/margin/calculator` 에 `[등록가 역산] / [마진 계산]` 탭). 사이드바 항목 1개 감소.

#### 7-4. 계산 과정 공개 (R-07 "밑에 수식을 써줬으면", R-09 "계산식도 밖으로 공개")

### R-10. 수익배분 커스텀 + 시뮬레이션 🔴 핵심

**현황**
- `/settlements/partner` 는 **완전 읽기 전용.** 조회만 되고 조정 UI가 없다.
- `partner_share_policy`: `partner_id`, `share_ratio`, `applies_year_month`(월별 override), 버전/유효기간.
- `settlement_policy`: `loss_policy`(CARRYOVER), `priority_distribution_json`(정액 우선분배), `close_day`.
- 현재 seed: 파트너 2명, 비율 6:4, 우선분배 100만/40만.
- **`partner` 테이블에 "이 사람이 동업자인지 직원인지" 구분이 없다.**

**기획 결정 — 사용자가 놓쳤을 수 있는 핵심 구분**

> 💡 **직원과 동업자는 회계적으로 완전히 다르다. 같은 표에 넣으면 순이익이 틀어진다.**
>
> - **직원 급여** = **비용**이다. 순이익을 계산하기 **전에** 차감된다.
>   (`expenses` 의 `LABOR` 카테고리 — 이미 enum에 있음)
> - **동업자 배분** = **이익 처분**이다. 순이익을 계산한 **후에** 나눈다.
>
> 직원을 배분 테이블에 비율로 넣으면 급여가 비용으로 안 잡혀 **순이익이 과대계상**되고,
> 세무 리포트의 손익이 실제와 어긋난다.

**[결정 D-294] `partner.participation_type` 3종 도입**

| 유형 | 처리 | 순이익 영향 | 예시 |
|---|---|---|---|
| `PARTNER` | 순이익 × 비율 | 배분 (차감 아님) | 동업자 |
| `EMPLOYEE_FIXED` | 고정 급여 → `expenses`(LABOR) 자동 생성 | **차감** | 월급제 직원 |
| `EMPLOYEE_INCENTIVE` | 고정급(비용) + 순이익 × 인센티브율(비용) | **둘 다 차감** | 성과급 직원 |

`partner` 확장 컬럼: `participation_type`, `fixed_monthly_amount`, `incentive_rate`,
`participation_start_ym`, `participation_end_ym`.

→ `participation_start_ym` 덕분에 **"3월까지 혼자, 4월부터 2명, 7월부터 직원 1명"** 같은
기간별 구성 변화가 자연스럽게 표현된다. 사용자가 요청한 "다양한 경우의 수"의 근간이다.

**배분 계산 순서 (확정)**

```
① 매출
② − 상품 직접비 (원가·수수료·광고·반품·풀필먼트·배송)
③ − 사업 공통비 (expenses, is_settlement_deductible)
   └ 여기에 EMPLOYEE_FIXED 급여와 EMPLOYEE_INCENTIVE 고정급이 포함된다
④ = 순이익
⑤ − EMPLOYEE_INCENTIVE 인센티브 (순이익 × 인센티브율)
⑥ − 이월 적자 상계 (carryover, 흑자월만)
⑦ = 분배 가능액
⑧ − 우선분배 (PRIORITY, 정액)
⑨ = 잔액 → PARTNER 들에게 share_ratio 비율 분배 (잔수는 마지막 파트너 귀속)
```

**시뮬레이터 (신규 화면 `/settlements/partner/simulator`)**

- **입력**: 기간(월 범위), 순이익(실제값 자동 로드 or 수동 입력), 참여자 목록(유형·금액·비율 편집 가능)
- **출력**: 참여자별 월별 수령액 + 기간 합계 + 1인당 실효 수령률
- **시나리오 저장/비교**: 최대 3개를 나란히 비교 (예: `현행 6:4` / `직원1명 채용` / `5:5 + 인센티브 10%`)
- **저장하지 않는다** — 시뮬레이션은 `monthly_settlement` 에 절대 쓰지 않는다.
  실제 적용은 `partner_share_policy` 를 새 버전으로 승인하는 별도 액션.
- **검증**: 비율 합 ≠ 1.0 이면 경고. 급여+인센티브가 순이익을 초과하면 적자 경고.

**월별 커스텀**: `applies_year_month` 를 이용해 특정 월만 비율 override.
화면에서 "이 달만 다르게" 토글 → 해당 월 정책 생성. `LOCKED` 정산월은 편집 불가.

   - 결제자별 필터 + 결제자별 합계 리포트.
3. **검색**: 키워드(적요·메모·거래처) + 기간 프리셋 + 카테고리 + 증빙상태 + 결제수단 + 결제자 다중 필터.

**AC**
- [ ] 비용 건에 이미지/PDF를 첨부하고 목록에서 첨부 여부가 보인다
- [ ] 첨부 시 증빙 상태가 자동으로 `PRESENT` 로 바뀐다
- [ ] 결제자를 지정·조회·필터할 수 있다
- [ ] 개인카드 결제 건이 시각적으로 구분된다
- [ ] 키워드·기간 복합 검색이 동작한다
- [ ] 세무사 제출용으로 기간 내 증빙을 ZIP으로 내려받을 수 있다

### R-13. 비용 카테고리 — 정상화

**현황**: B-04. FE가 존재하지 않는 `/expense-categories` API를 호출하고,
DB에 없는 컬럼(`code`, `parent_id`)을 폼에서 다룬다. **현재 이 화면은 동작하지 않는다.**

**기획 결정**
1. **API 경로 확정** — 새 라우터를 만들지 않고 **기존 `/policies/expense_category` 를 쓴다.**
   카테고리는 `effective_from`/`version` 을 가진 **정책**이다. 별도 CRUD를 만들면 정책 이력 관리가 깨진다.
   FE `lib/api/categories.ts` 를 정책 API 호출로 교체.
2. **필드 정합** — FE 폼을 실제 컬럼에 맞춘다:
   `name`, `kind`(COGS/MARKETING/LOGISTICS/OFFICE/UTILITY/LABOR/TAX/FEE/SUBSCRIPTION/OTHER),
   `default_tax_deductible`, `default_settlement_deductible`, `sort_order`, `memo`
3. **계층(parent) 지원 여부** — [결정] **MVP에서는 도입하지 않는다.**
   `kind` 가 이미 대분류 역할을 한다. 2단계 분류로 충분하고, 계층을 넣으면
   세무 리포트 집계 로직이 재귀가 되어 복잡도가 급증한다. 필요해지면 그때 `parent_id` 추가.
4. **삭제 보호**: 사용 중인 카테고리는 삭제 불가 → 비활성화(`is_active=false`)만 허용.
   삭제 시도 시 "이 카테고리를 쓰는 비용 N건이 있습니다" 안내.
5. **세무 연계**: 각 카테고리에 `default_tax_deductible`(손금 인정 여부) 기본값을 두어
   비용 입력 시 자동 채움. 세무사 검토 부담을 줄이는 핵심.
6. 카테고리별 사용 건수·합계를 목록에 표시 → 안 쓰는 카테고리 정리 가능.

**AC**
- [ ] 카테고리 목록이 실제로 로드된다 (404 없음)
- [ ] 추가·수정·비활성화가 동작하고 새로고침 후 유지된다
- [ ] 사용 중인 카테고리는 삭제되지 않고 이유가 안내된다
- [ ] 카테고리 선택 시 비용 폼의 공제 여부가 자동 채워진다
- [ ] 카테고리별 사용 건수와 합계가 표시된다

## 6. 이번에 채워 넣은 것 (사용자가 명시하지 않았으나 필요한 부분)

사용자 요청: *"내가 잘 모르는 부분이 있을 수도 있어서 한번 더 확인해보고 필요한 부분은 다 채워서"*

1. **직원 vs 동업자 회계 구분** (R-10) — 이걸 안 나누면 순이익이 틀어진다. 가장 중요한 보완.
2. **부가세 계산이 현재 틀렸다는 사실** (R-07) — "단순한 것 같다"는 직관이 실제로 오류였다.
3. **마켓 수수료의 VAT 포함/별도 구분 부재** (R-07-2) — 요청에 없었지만 마진이 10% 어긋나는 원인.
4. **팝업 투명 문제가 6개 화면에 걸친 단일 원인**이라는 점 (B-01).
5. **대시보드 위젯 3개가 이미 깨져 있다는 사실** (B-02) — "그래프 개선" 이전 문제.
6. **비용 카테고리 화면이 아예 동작하지 않는다는 사실** (B-04).
7. **Webhook URL의 보안 등급** (R-02) — 자격증명으로 취급해야 함.
8. **증빙 첨부 → 증빙 상태 자동 연동** (R-12) — 세무 리포트와 직결되는데 요청에 없었음.
9. **정산 대사 리포트** (R-11) — "정산 기록"의 실제 목적. 기록 저장만으로는 쓸모가 없다.
10. **모달/드로어/페이지 사용 규칙** (X-02) — 현재 혼재. 규칙 없이 만들면 계속 혼재한다.
