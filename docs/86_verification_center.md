# 86. 검증센터 — 원천과 파생을 맞대어 차이만 남긴다

2026-08-17. 선행: `83_settlement_financial_posting.md`, `84_autopilot_phase1_audit.md`,
`85_local_operation_mode.md`.

사용자가 실제 웹을 보기 시작했다. 그런데 화면의 숫자가 맞는지 사람이 378건을
일일이 확인할 수는 없다.

이번 작업의 목표는 하나다.

```
숫자를 믿으라고 요구하지 않는다.
시스템이 스스로 원천과 맞대어 보고, 사람은 차이가 있는 것만 확인한다.
```

---

## 1. 절대 하지 않은 것

```
Seller OS 계산값 → expected 로 복사 → 같은 값과 비교 → PASS
```

이것은 자기검증이고 아무것도 지키지 못한다. 계산이 어떻게 망가지든 통과한다.

그래서 비교 대상을 이렇게 잡았다.

| 검증 | 왼쪽 (독립) | 오른쪽 (파생) |
|---|---|---|
| 정산 금액 | 정산서가 준 상품매출·배송비·쿠폰·수수료 | 그것으로 재구성한 순매출 vs 벤더 정산금액 |
| 수집 | 실행 기록의 `read_count` | 처리한 건수의 합 |
| 계산 추적 | 장부·정산서·마스터의 원 성분 | 저장된 마진 |
| 기준 사례 | **사람이 원천을 보고 승인한 값** | 지금 계산 결과 |

마지막 줄이 이번 작업의 핵심 장치다.

---

## 2. 조사 결과 — 무엇이 이미 있었나

만들기 전에 실측했다.

| 이미 있던 것 | 그래서 |
|---|---|
| `IngestResult.reconciles` (주문·클레임 각각) | **대사 등식을 새로 만들지 않았다.** 그 등식을 저장된 값으로 다시 볼 뿐 |
| `settlement_components.load_all` ("대사·검증 화면이 쓴다") | 그대로 재사용 |
| `operation_issue` + 예외 센터 | 새 예외 체계를 만들지 않고 읽어 합쳤다 |
| `calculation_snapshot_json` | **새 칸을 만들지 않고** 여기에 근거를 넣었다 |
| `profit_status` 4단계 · `not_final_reasons` | 신뢰도 표시에 참고 |
| `margin.py` 의 권한 조합 | 검증센터가 같은 조합을 쓴다 |

### 2-1. 대사 등식은 도메인마다 다르다

지시서 §6 은 하나의 식을 제시했지만 실데이터가 아니라고 답했다.

```
주문   read = created + updated + skipped + conflict + rejected      ✅
클레임 read = rejected + created + updated + unchanged               ✅
클레임에 주문 식을 대면  16 ≠ 16+14  → 항상 어긋난다                ❌
```

클레임의 `conflict_count` 는 배타적 분류가 아니다. "사람이 봐야 하는 건"
(원 주문 미매칭 + 금액 미해결)을 **가로질러** 세는 값이라 등식에 넣으면 안 된다.
`claim_ingest.IngestResult.reconciles` 가 쓰는 식이 진짜다.

## 3. CALCULATION_EVIDENCE_GAP_FOUND = YES

지시서 §17 이 요구한 보고다.

### 3-1. 무엇이 없었나

```
product_margin_actual        374행
  calculation_snapshot_json  20행만 있음  (정산 매칭된 것)
                            354행 NULL   (전체의 94.6%)
  applied_policy_versions_json  374행 전부 NULL
```

그리고 있는 20행도 정산 컴포넌트만 담고 있었다. 정책 추정 경로는 코드가
`{"basis": "LEDGER_AND_POLICY"}` **한 줄**만 남긴다 — 원가가 어디서 왔는지도,
수수료를 어떤 근거로 뗐는지도 알 수 없다.

즉 **"이 마진이 왜 이 숫자인가" 에 답할 수 없는 상태**였다.

### 3-2. 무엇을 더했나 (최소 · generic)

`calculation_snapshot_json` 에 성분별 근거를 넣는다. **새 컬럼도 새 테이블도
만들지 않았다.**

```json
{
  "basis": "LEDGER_AND_POLICY",
  "formula": "margin = revenue - cost - shipping - marketplace_fee - ...",
  "components": {
    "revenue":         {"value": 10000, "source": "ORDER_LEDGER", "confidence": "ESTIMATED"},
    "cost":            {"value": 4000,  "source": "ORDER_PURCHASE_COST", "confidence": "ACTUAL"},
    "marketplace_fee": {"value": 1100,  "source": "POLICY", "confidence": "ESTIMATED"}
  },
  "warnings": [...]
}
```

성분마다 `value / source / confidence` 셋뿐이다. **벤더별 필드를 늘리지
않는다** — 판매처가 늘어도 이 구조는 그대로다.

### 3-3. 과거 354행은 자동으로 고치지 않았다

§53 대로 자동 재계산하지 않는다. 검증센터가
`CALCULATION_TRACE_INCOMPLETE 354건` 으로 보고하고, 계산 추적을 열면
`RECONSTRUCTED`(지금 원천에서 되짚음)임을 명시한다.

```
SNAPSHOT       계산 당시 박제된 근거 — 그때 실제로 쓴 값
RECONSTRUCTED  지금 원천에서 되짚은 값 — 그동안 원천이 바뀌었으면 다르다
```

둘을 같게 보여주면 원가를 고친 뒤에도 "이 마진은 이 원가로 계산됐다" 는
틀린 설명을 하게 된다.

## 4. CORE_DOMAIN_GAP_FOUND = YES — 기준값을 담을 곳이 없었다

§60 이 요구한 보고다. 마이그레이션 하나(M059)를 추가했다.

### 4-1. 왜 필요한가

저장소 어디에도 **"사람이 원천을 보고 이 값이 맞다고 확인했다"** 를 담는
칸이 없다. `product_margin_actual` 은 우리가 계산한 값이고,
`marketplace_settlement_record` 는 벤더가 준 값이다 — 둘 다 파생·수신이지
사람의 판정이 아니다.

### 4-2. 재무 진실의 중복 저장이 아니다

§60 이 금지하는 것은 "검증 편의를 위해 재무 사실을 복제하는 것" 이다.
`verification_golden_case` 는 다르다.

```
어떤 화면도 여기서 금액을 읽어 표시하지 않는다.
회귀 검사만 읽는다.
```

### 4-3. 승인 전에는 기준값이 없다

```
CANDIDATE  expected_json IS NULL   ← 자동 선정. 값 없음
APPROVED   expected_json 필수      ← 사람이 넣어야 도달
```

DB CHECK 가 강제한다. 그리고 `verification_golden.py` 에는 **현재 계산값을
expected 로 넣는 경로가 아예 없다** — 테스트가 소스에서 그런 코드가 없음을
확인한다(`test_the_module_has_no_path_that_copies_current_results_into_expected`).

기준값을 두 번째로 고칠 때는 사유가 필수다(`revision` + `change_reason`,
DB CHECK). 조용히 덮을 수 있으면 계산이 틀렸을 때 기준을 고쳐 통과시킬 수
있고, 그게 회귀 검사를 무력화하는 가장 쉬운 방법이다.

## 5. 세 상태를 섞지 않는다

```
PASS          검증했고 맞다
FAIL          검증했고 틀리다
NOT_VERIFIED  검증할 근거가 없다      ← PASS 로 세지 않는다
NOT_AVAILABLE 검증 대상 자체가 없다   ← 실패가 아니다
```

합이 판정 수와 같은지 백엔드 테스트와 E2E 가 모두 고정한다. 이걸 놓치면
"환불 정산 표본이 없다" 가 "환불 정산이 맞다" 로 보인다.

## 6. 실측하며 고친 두 가지 (검증센터 자신의 오진)

검증 도구가 거짓 경보를 내면 아무도 안 믿게 된다. 실 DB 로 돌려 두 개를 잡았다.

### 6-1. 정산 중복 8건 — **오진이었다**

처음에 `(import_batch_id, line_reference, row_type)` 을 중복 키로 썼다.
그런데 배송료 행의 `line_reference` 는 `<기본배송료>` 같은 **라벨**이라 한
파일에 여러 번 나오는 것이 정상이다.

```
잘못된 키   중복 8건 (전부 오탐)
실제 식별자 import_idempotency_key / source_row_fingerprint  → 중복 0
```

적재기가 선언한 식별자로 바꿨다.

### 6-2. 수집 대사 실패 6건 — **판정 대상이 아니었다**

6건 전부 2026-08-16 20:07 이전 실행이었다. 그 시점이 M057 이 CLAIMS 와
ORDERS 를 나눈 순간이고, 이전 `ORDERS` 행에는 클레임 실행이 섞여 있다
(docs/84 §7, 재분류 불가).

FAIL 로 세면 고칠 수 없는 과거가 영구히 빨간불로 남고 진짜 실패가 묻힌다.
**경계를 지어내지 않고** 첫 `CLAIMS` 기록 시각을 경계로 삼아
`NOT_VERIFIED` 로 분리했다.

같은 이유로 주문 건수 비교도 그 시점 이후 기록만 쓴다 — 안 그러면
"장부보다 12건 많다" 는 없는 차이가 만들어진다.

## 8. 사용자가 실제로 할 일

```
378건 전수 확인   ✗
검증센터 확인 + Golden 16건 직접 확인 + 예외만 확인   ✓
```

후보 16건이 6가지 상황을 대표한다. 같은 모양 20건을 확인해 봐야 한 가지
경우만 검증된다.

| 케이스 | 건수 | 확인할 원천 | 확인할 금액 |
|---|---|---|---|
| 정산 매칭 | 5 | 판매처 정산서 | 상품매출·배송비매출·판매수수료 |
| 배송비 매출 있음 | 2 | 판매처 정산서 | 배송비를 매출에 넣는 결정(D1)이 맞는가 |
| 판매자 쿠폰 있음 | 1 | 판매처 정산서 | 쿠폰을 매출 차감으로 보는 결정(D2)이 맞는가 |
| 정책 추정만 | 4 | 판매 장부 + 수수료 정책 | 판매금액·추정 수수료·원가 |
| 다중 라인 | 2 | 판매 장부 | 라인별 합산 |
| 취소·반품 연결 | 2 | 판매처 클레임 화면 | 취소 수량과 매출 조정액 |

**환불 정산 사례는 만들지 않았다** — 확인할 원천이 없는 것을 확인하라고
할 수 없다.

승인된 기준값: **0건.** 이번 세션에서 사용자가 직접 확인하지 않았으므로
임의로 승인하지 않았다(§58).

## 9. 쓰는 법

```
운영 → 검증센터
```

| 언제 | 무엇을 |
|---|---|
| 월초·월말 | 전체 대사가 확인됨인지, 확인 필요가 몇 건인지 |
| 정산서를 넣은 뒤 | 정산 금액 차이 0원인지, 매칭 못 한 행이 몇 건인지 |
| 코드·정책을 바꾼 뒤 | 기준 사례 회귀가 통과하는지 |
| 숫자가 이상할 때 | 그 주문의 계산 추적 — 성분마다 출처와 신뢰도가 붙는다 |

**FAIL 이 보여도 자동으로 고치지 않는다.** 근거를 먼저 보고, 고치는 것은
각자의 명시적 흐름(재계산·정산 재매칭·원가 수정)이 한다.

---

## 9-1. 실측하며 알게 된 것 하나 더 — 재고는 대사할 대상이 없다

§35 는 "내부 재고 원장 불변식(원장 합계 vs 잔량)" 을 검사하라고 한다.
**이 저장소에는 저장된 잔량 칸이 없다.** 잔량은 `SUM(quantity_delta)` 로
그때그때 구한다(`inventory._BALANCE_SELECT`).

즉 둘이 어긋날 구조가 아니고, 그걸 검사해 `PASS` 라고 적는 것은 아무것도
확인하지 않고 통과 도장을 찍는 것이다. 대신 실제로 깨질 수 있는 것을 본다.

```
음수 잔량        받은 것보다 많이 나갔다
고아 상품 참조    상품이 사라졌는데 재고 이동만 남았다
중복 적재        같은 출처가 두 번 들어왔다 (import 멱등 위반)
```

외부 대사는 판매처가 API 를 주지 않아 `NOT_AVAILABLE` 이다.
