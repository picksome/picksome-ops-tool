## 0. 한 줄 요약

외부 연동에 자격증명을 붙이면서 **비밀이 실제로 새고 있던 결함 하나**를 찾아 고쳤고,

심었다.

## 1. 실제로 새고 있던 결함 — 422 응답이 제출값을 돌려줬다

자격증명 API 를 만들기 전에 기존 오류 처리부터 봤다.

`validation_error_handler` 가 `RequestValidationError.errors()` 를 그대로 응답
본문에 넣고 있었다. Pydantic v2 의 오류 항목에는 **사용자가 제출한 값이 `input`
으로 들어 있다.**

```python
M(api_secret="SECRET_TEST_VALUE_123")   # min_length 위반
# errors()[0]["input"] == "SECRET_TEST_VALUE_123"
```

즉 자격증명 입력이 검증에 걸리는 순간 그 값이 422 응답으로 돌아왔다. 브라우저
콘솔, 프록시 접근 로그, Playwright trace 어디에나 남는다. 가정이 아니라 재현해서
확인했다.

### 고친 방법과, 한 번 틀렸던 것

처음에는 **비밀처럼 생긴 키**(`api_secret` 등)의 `input` 만 지웠다. 그런데
사용자가 비밀을 엉뚱한 칸에 붙여넣으면 그 칸은 비밀 키가 아니라 그대로 새어
나온다. `vault_entry_id` 에 비밀을 넣은 테스트가 이걸 잡았다.

키 이름으로 판단하는 방식은 **제출값에는 통하지 않는다.** 그래서 `input` 을
항상 뺀다. 잃는 것은 거의 없다 — `loc`(어느 필드)와 `msg`(무엇이 잘못됐나)는
남고, 사용자는 자기가 무엇을 입력했는지 이미 안다.

`app/core/redaction.py` 가 이 규칙을 갖는다. 값의 생김새(긴 랜덤 문자열)로
추측하지 않는 이유도 같은 파일에 적었다 — 그러면 상품 설명이나 메모가 `***`
로 보이고 사용자는 이유를 알 수 없다.

## 2. 자격증명은 **값이 아니라 보관 위치**를 연결한다

조사 결과 프로젝트 전체에 암호화 저장소가 없다. 의도적이다.

```
inbound  (봇이 우리에게)     argon2 해시     검증만 가능, 복원 불가
outbound (우리가 외부에게)   vault 참조만    password_vault_entry
```

CLAUDE.md: "실제 비밀번호를 저장하지 않고 **보관 위치만** 저장한다."

그래서 M040 도 암호화 저장소를 새로 만들지 않는다. 추가한 것은 "설정됐다는
사실과 그 시점" 뿐이다 — `credential_updated_at/by`, `credential_kind`,
`last_test_status/at/message`.

- `POST /external/accounts/{id}/credentials` 는 `vault_entry_id` 와
  `credential_kind` **두 개만** 받는다. 비밀 값을 받는 필드가 없다.
- 계정 응답은 `credential_configured` 불리언만 준다. vault 항목 id 조차 나가지
  않는다.
- ADMIN 전용이다. 계정 이름을 고치는 것과 인증정보를 바꾸는 것은 무게가 다르다.
- 교체가 실패해도 기존 연결은 남는다(서버가 검증 후 갱신).
- 해제는 연결만 끊는다. 보관함 항목은 우리 것이 아니다.

### ⚠️ 남은 결정 — 무인 동기화에 필요한 복원 가능한 비밀

셀러툴을 스케줄로 동기화하려면 호출 시점에 **복원 가능한** 비밀이 필요하다.
해시로는 안 되고, "Bitwarden 의 어떤 항목" 이라는 이름만으로도 무인 실행은
안 된다. 선택지는 둘이다.

```
(a) 암호화 저장소 도입 + 키 관리(KMS·env key rotation)
(b) 실행할 때 사람이 비밀을 넣는 반자동 방식
```

**보안 태세를 바꾸는 결정이라 임의로 고르지 않았다.** 지금은 실제 커넥터가
없어 아무것도 막히지 않는다. M040 docstring 에도 같은 내용을 남겼다.

## 3. 연결 시험 — 실패 사유를 뭉치지 않는다

```
CONNECTOR_UNAVAILABLE       우리가 아직 구현 안 함
CREDENTIAL_NOT_CONFIGURED   설정이 안 됨
AUTHENTICATION_FAILED       값이 틀림
CONNECTION_FAILED           네트워크·상대 서버
RATE_LIMITED                잠시 후 다시
```

전부 "연결 실패" 로 보여주면 사용자는 무엇을 고쳐야 할지 알 수 없다 — 자기
자격증명을 의심하면서 실제로는 우리 쪽 미구현인 경우가 가장 흔하다. 화면도
다섯 가지를 서로 다른 문구로 쓴다. 외부 오류 메시지는 200자로 자르고 그대로
저장하지 않는다 — 토큰이 섞여 오는 일이 있다.

## 4. 동기화 데이터 품질 (월 마감 점검에 추가)

| 코드 | 등급 | 뜻 |
|---|---|---|
| `CREDENTIAL_NOT_CONFIGURED` | INFO | 계정은 있는데 연결이 없다 |
| `SYNC_FAILED` | WARNING | 계정별 최근 실행이 실패 (계정당 1건으로 합침) |
| `SYNC_PARTIAL_FAILURE` | WARNING | 일부만 들어왔다 — 성공으로 뭉치지 않는다 |
| `SYNC_CONFLICT` | WARNING | 사람이 고친 값을 외부가 덮으려 했다 |
| `EXTERNAL_ACCOUNT_DISABLED_WITH_ACTIVE_MAPPING` | INFO | 꺼둔 계정에 살아 있는 매핑 |
| `EXTERNAL_MAPPING_ORPHAN` | WARNING | 가리키는 내부 항목이 없다 |

**`SYNC_STALE` 은 넣지 않았다.** "며칠 안 돌면 오래된 것인가" 에 대한 근거가
없다. 하루에 한 번 도는 연동과 월 1회 정산 파일은 기준이 다르고, 아직 실제
연동이 하나도 없어 관측된 주기가 없다. 임의 임계값을 넣으면 그 숫자가 근거처럼
굳는다.

## 5. 충돌 목록이 원가 조회 권한을 우회하고 있었다

충돌 행에는 **양쪽 값이 다 들어 있다** — "외부는 3,900 이라 하고 우리는 4,200
이다". 원가 필드면 이 목록이 `sourcing.view_cost` 를 우회하는 통로가 된다.

지금 이 endpoint 를 볼 수 있는 세 역할(ADMIN/OPERATOR/SOURCING)은 모두 원가
조회 권한이 있어 **현재 실제로 새지는 않는다.** 그래도 서버에서 막았다 —
역할이 하나 늘어날 때 아무도 이 화면을 떠올리지 않을 것이기 때문이다.

값은 지우되 필드명은 남긴다. 가려졌다는 사실까지 숨기면 사용자는 목록이 비어
보이는 이유를 알 수 없다. 프론트는 "값 없음(—)" 과 "가려짐" 을 다르게 그린다.

## 6. 공급처 Excel — 평문 비밀번호가 있는 파일

이전 세션들에서 없던 `도매 매입 사이트들.xlsx` 가 이번엔 있었다.

```
시트 "공급업체"  145행 × 25열
헤더: 공급업체 | 공급업체 유형 | 문의 | 주소 | 웹사이트 | 평점(주관적)
      | 메모 | ID | PW | 참조
```

**`ID` 와 `PW` 열에 실제 로그인 정보가 평문으로 들어 있다.**

importer 는 이 두 열을 **읽어서 버린다.** 값을 저장하지도, 반환하지도, 로그에
남기지도 않는다. 만드는 유일한 산출물은 `credential_present` 불리언 — "이
공급처에는 로그인 계정이 있다" 는 사실뿐이다. `supplier_site.credential_present`
는 M037 이 이미 만들어 둔 칸이다. 비밀은 사람이 보관함으로 옮기고 우리는
`password_vault_entry` 로 위치만 가리킨다.

### 매핑 (추측하지 않았다)

| Excel 열 | 대상 | 비고 |
|---|---|---|
| 공급업체 | `name` | 필수. 없으면 그 행은 버리고 **보고**한다 |
| 공급업체 유형 | `handling_categories` (M041) | `supplier_type` 이 **아니다** |
| 문의 | `contact_name` (M041) | |
| 주소 | `address` (M041) | |
| 웹사이트 | `website_url` + `website_domain` | |
| 평점(주관적) | `rating` | `???` 는 0 이 아니라 **NULL** |
| 메모 | `memo` | |
| 참조 | `reference_note` (M041) | 메모와 섞지 않는다 |
| ID / PW | **버림** | `credential_present=true` 만 |

`supplier_type` 에 품목군을 넣지 않은 이유: `supplier_type` 은 `WHOLESALE /
MANUFACTURER / ...` 처럼 **거래 형태**이고, Excel 의 "공급업체 유형" 은
"생활/잡화, 펫" 처럼 **무엇을 파는가**다. 다른 축이고 한 공급처가 여럿을
취급한다. 열거형에 밀어 넣으면 둘 다 못 쓰게 된다. 품목군 정규화는 분류 체계를
먼저 정해야 하는 일이라 지금은 원문 그대로 담는다.

### 열은 위치가 아니라 이름으로 찾는다

열 순서는 사람이 언제든 바꾼다. 위치로 읽으면 어느 날 조용히 담당자 이름이 주소
칸에 들어간다. 모르는 헤더는 추측하지 않고 `unmapped_headers` 로 보고한다.

### 덮어쓰지 않는다

이미 있는 공급처는 **비어 있는 칸만 채운다.** 값이 다르면 `differences` 로
보고만 하고 그대로 둔다. 앱에서 고친 값을 Excel 이 되돌리면 사용자는 같은 수정을
매번 반복하게 된다. Excel 칸이 비었다고 우리 값을 지우지도 않는다.

### 실제 파일 파싱 결과

```
공급처 54건 · 빈 행 90개(시트 여백) · 이름 없어 버린 행 0
중복 코드 0 · 평점 미기입(모름) 25건 · 로그인 계정 있음 54건
웹사이트 칸이 주소가 아닌 행 1건 (2행) — 지우지 않고 보고만
```

파싱하면서 두 가지를 고쳤다.

1. 2행의 웹사이트 칸에 **상호명**이 적혀 있어 그게 도메인으로 잡혔다. 점 없는
   호스트는 도메인이 아니라고 판정하게 바꿨다 — 안 그러면 상호명으로 중복
   판정까지 오염된다.
2. 이름이 전부 한글인 공급처는 ASCII 로 남는 게 없어 코드가 고정값으로
   떨어졌다. **서로 다른 공급처가 같은 코드**를 갖게 된다. 이름 해시를 붙여
   갈라놓았다(이름이 같으면 코드도 같으므로 재실행에 안정적이다).

### 실행

```
python -m scripts.import_supplier_sites "…/도매 매입 사이트들.xlsx" \
       --org <UUID> --actor <UUID>          # 미리보기 (기본)
       … --apply                            # 실제 반영
```

**기본이 미리보기다.** 자동 실행 대상이 아니다 — 앱 기동이나 seed 에 걸지
않는다. 운영 DB 에 개발용 Excel 이 흘러드는 경로를 만들지 않기 위해서다.

## 7. 대안 소싱처 비교표

Product Drawer 의 소싱 탭에 소싱처가 둘 이상일 때 나온다.

```
공급처 | 예상 원가 | 적용 원가 대비 | MOQ | 리드타임 | 최근 확인 | 주 소싱처
```

**순위를 매기지 않는다.** "최저 landed cost = 추천 공급처" 로 만들지 않았다.
실제 선택에는 여기 없는 것들이 들어간다 — MOQ 를 감당할 현금, 시즌과 리드타임,
클레임 이력, 카드 결제 가능 여부. 숫자 하나로 줄을 세우면 그것들이 사라진다.
점수도 추천 배지도 없고, 정렬 기준만 사용자가 고른다.

계산 못 하는 줄은 "계산 불가 + 무엇이 없는지" 로 쓴다. 0 으로 채우면 정확히
반대로 — **가장 싼 곳으로** — 보인다. 정렬에서도 값이 없는 줄은 항상 아래다.

서버가 한 번에 계산한다(`GET /products/{id}/source-comparison`). 화면에서 landed
cost 를 다시 계산하면 두 산식이 갈라지는 순간 어느 쪽이 맞는지 알 수 없다.

주 소싱처를 바꿔도 `product.cost_amount` 는 바뀌지 않는다. 채택은 여전히
`COST_CHANGE` 승인이다.

## 8. Playwright 간헐 timeout — **미해결**

지난 세션에서 `expense-screen.spec.ts` 의 "잠긴 달 정정" 이 한 번 46.8초에서
죽었다(제한 45초). 단독 실행 17.7초, 이후 전체 실행에서도 재현되지 않았다.

**이번에도 재현되지 않았다.** 전체 171개를 두 번 연속 돌렸고 두 번 다 통과했다
(8.2분 / 8.1분). 해당 테스트는 3.9초였다.

원인을 확정하지 못했으므로 **미해결로 둔다.** 하지 않은 것:

```
timeout 45 → 90    증상만 밀어낸다. 90초에서 또 죽으면 그때는 무엇을 볼까
retries 0 → 1      빨간 불을 초록으로 덮는다. 그 순간부터 아무도 안 믿는다
```

대신 다음에 느려질 때 **어디서** 느렸는지 알 수 있게 구간 측정을 심었다
(`e2e/timing.ts`). 한 번의 실패에서 나온 총 시간 하나로는 로그인인지, dev
서버의 라우트 컴파일인지, drawer 열기인지, 저장 왕복인지 구분할 수 없다.

정상 실행의 기준값 (`E2E_TIMING_VERBOSE=1`):

```
총 측정 구간 3491ms (제한 45000ms)
   1767ms  reseed
    146ms  로그인
    882ms  페이지 이동
     85ms  dialog 대기
    114ms  조정 대화상자 열기
     47ms  입력
    128ms  저장 왕복
    322ms  DB 확인
```

지난 세션에 "reseed 0.26초" 라고 적었는데 계측해 보니 **1.77초**다. 그래도 총
3.5초라 46.8초와는 12배 차이고, reseed 만으로 설명되지 않는다.

가장 유력한 가설은 남겨 둔다: 프론트를 `next dev` 로 띄우므로 라우트를 처음
방문할 때 **on-demand 컴파일**이 일어난다. 로그에서 실제로
`○ Compiling /operations/system … ✓ 633ms` 같은 줄이 보인다. 어떤 사정으로 이
컴파일이 수십 초 걸리면 그 순간 45초를 넘긴다. 다만 **확인된 것이 아니라**
가설이다 — 확인되면 워밍업을 globalSetup 이 아니라 별도 setup 프로젝트로
넣어야 한다(globalSetup 과 webServer 기동 순서가 보장되지 않는다).

측정은 통과했을 때도 붙는다. 정상값이 있어야 늘어난 실행과 비교할 수 있다.
