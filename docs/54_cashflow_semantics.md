# 54. 현금흐름 — 무엇을 "실제 돈" 이라고 부를 수 있는가

> Phase 2~3 의 결론. 구현보다 **의미 확정이 먼저**다.
> 여기서 틀리면 그 위에 만드는 화면·집계가 전부 거짓이 된다.

---

## 1. 가장 중요한 원칙

**손익과 현금흐름을 합치지 않는다.**

```
8월 매출     30,000,000     ← 손익
8월 순이익    6,000,000     ← 손익

8월 실제 입금 19,000,000     ← 현금
8월 실제 출금 17,000,000     ← 현금
```

매출 발생일 ≠ 입금일. 비용 발생일 ≠ 지급일. 배분 계산일 ≠ 지급일.

이미 `monthly_close_snapshot` 이 손익을 확정하고 있다. 현금흐름은 **그것과 다른
질문**에 답한다: "지금 통장에 얼마가 들어오고 나가는가."

---

## 2. 세 가지 상태

| 상태 | 뜻 | 근거 |
|---|---|---|
| `EXPECTED` | 그렇게 될 것 같다 | 아직 확정되지 않은 예정 |
| `CONFIRMED` | 상대가 금액을 확정했다 | 정산서·승인된 지급 항목 |
| `ACTUAL` | **돈이 실제로 움직였다** | 지급/입금 기록이 존재 |

`EXPECTED` 를 실제 돈으로 표시하지 않는다.

---

## 3. 조사 결과 — 각 source 를 어디까지 부를 수 있나

### 3-1. 실제 출금 — `payout_payment` → **ACTUAL 가능** ✅

```
payout_payment(payment_date, amount, payment_reference, evidence_attachment_id)
```

**근거가 있다.** 사람이 "이 날 이 금액을 보냈다" 고 기록한 행이고,
증빙 첨부까지 붙는다. `payout_item.paid_amount` 는 이 행들의 합계를 DB 트리거가
유지한다(M029) — 지급 기록 없이 `PAID` 가 될 수 없다.

포함되는 것: 파트너 배분 지급, 직원 급여, 개인카드 상환.

### 3-2. 실제 입금 — **ACTUAL 로 부를 수 있는 source 가 없다** ❌

조사한 것과 결론:

| 후보 | 왜 ACTUAL 이 아닌가 |
|---|---|
| `marketplace_settlement_record.settled_at` | **스키마에 정의가 없다.** M001 에 주석이 없고, 이 값이 실제 은행 입금일인지·정산 확정일인지·지급 예정일인지 구분할 근거가 어디에도 없다. 레코드도 0건이라 실물로 확인할 수도 없다 |
| `net_settlement` | 같은 이유. "정산액" 이 통장에 들어온 금액인지 알 수 없다 |
| 판매처 지급 API | 없다 (`BLOCKED_CREDENTIAL`) |
| 은행 입금 기록 | 없다 (은행 API 미연동) |

> **`settled_at` 이라는 이름만 보고 ACTUAL 로 간주하지 않는다.**
> 이름은 근거가 아니다. 이걸 실제 입금으로 쓰면 "이번 달 2천만원 들어왔다" 가
> 화면에 뜨는데 통장에는 아무것도 없을 수 있다.

**결론**: 정산 레코드는 최대 `CONFIRMED` 까지다. 그리고 지금은 레코드 자체가
0건이므로 실질적으로 **입금 쪽 현금흐름은 데이터가 없다.**

```text
BLOCKED_EXTERNAL_DATA:
실제 입금을 ACTUAL 로 표시하려면 (a) 판매처 지급 API 의 paid/completed 레코드,
(b) 은행 입금 내역, (c) 사람이 "이 날 얼마 들어왔다" 고 확인한 기록
중 하나가 필요하다. 셋 다 없다.
```

### 3-3. 비용 지급 — **지급일 컬럼이 없다** ❌

`expenses` 에는 `expense_date`(발생일)만 있고 **지급일이 없다.**
카드 결제는 발생일과 결제일이 한 달 가까이 차이 난다.

그래서 "비용이 장부에 있으니 그날 현금이 나갔다" 고 가정할 수 없다.
개인카드 비용은 `payout` 을 통해 상환되므로 그 경로에서만 ACTUAL 이 된다.

---

## 4. 그래서 무엇을 만들 것인가 — source-linked read model

**generic cashflow 행을 복제 생성하지 않는다.**

`payout_payment` 를 그대로 두고 cashflow row 를 또 만들면, 지급 취소가 일어났을 때
두 곳을 고쳐야 하고 하나만 고쳐지는 순간 이중 계상이 된다.

```
읽기 모델 (계산)          ←  payout_payment        ACTUAL 출금
                          ←  payout_item(미지급)   EXPECTED 출금
                          ←  marketplace_settlement CONFIRMED 입금 (데이터 없음)
                          ←  manual_cash_event     사람이 기록한 것만
                          ←  cash_balance_baseline 기준 잔액
```

새 테이블은 **기존 source 로 표현할 수 없는 것**만 만든다:

| 새로 필요한 것 | 이유 |
|---|---|
| `manual_cash_event` | 은행 API 가 없는 사용자가 "이 날 얼마 들어왔다/나갔다" 를 직접 기록. **유일한 실제 입금 근거가 될 수 있는 경로** |
| `cash_balance_baseline` | 시작 잔액. 이게 없으면 예상 잔액을 계산할 수 없다 |

### 이중 계상 방지

`manual_cash_event` 는 `source_type`/`source_id` 를 갖고,
**이미 `payout_payment` 로 기록된 지급을 수동 출금으로 또 넣을 수 없게** 한다.
그 조합에 UNIQUE 를 걸어 DB 가 막는다.

---

## 5. 은행 잔액이라고 부르지 않는다

은행 API 가 없다. 그래서 화면에 쓰는 말은:

```
기준 잔액        ← 사용자가 입력한 값 + 그 시점
예상 잔액        ← 기준 잔액 + 예상 유입 − 예상 유출
```

**"은행 실잔액", "현재 계좌 잔액" 이라고 쓰지 않는다.**
기준 잔액을 입력하지 않았으면 잔액 계산 자체를 보여주지 않는다 —
0원에서 시작한 것처럼 그리면 "통장에 0원" 으로 읽힌다.

---

## 6. ZERO 와 UNKNOWN 의 구분

이 도메인에서 특히 중요하다.

| 표시 | 뜻 |
|---|---|
| `0 원` | 실제로 0원이다 (이 달에 지급이 없었다) |
| `—` + "정산 미연결" | 모른다 (정산 데이터가 없다) |
| `—` + "기준 잔액 미설정" | 계산할 수 없다 |

`?? 0` 으로 떨어뜨리면 셋이 전부 "0원" 이 된다. 이 프로젝트에서 이미
같은 실수가 있었다(D9 — 알림 배지가 항상 0).

### 구현하면서 확정된 것

**이중 계상은 두 겹으로 막는다.**
M034 의 부분 UNIQUE 는 "같은 원본을 두 번" 만 막는다. 원본과 **나란히** 서는 것은
막지 못한다 — `payout_payment` 한 줄과 그걸 가리키는 수동 기록 한 줄이 둘 다
집계되면 출금이 두 배가 된다. 그래서 읽기 모델이 `AGGREGATED_SOURCE_TYPES` 를
가리키는 수동 기록을 합계에서 제외하고, 서비스가 생성 시점에 먼저 거절한다.
(설계 단계에서 놓쳤고 구현 중에 발견했다.)

**대시보드는 권한의 뒷문이 될 수 있다.**
`/reports/dashboard` 는 OPERATOR·READONLY 도 읽지만 `/cashflow` 는 아니다.
카드를 그냥 넣었더니 403 을 받는 사람에게 예상 잔액·미지급액이 그대로 나갔다.
역할 목록을 `cashflow.VIEW_ROLES` 한 곳에 두어 두 라우터가 갈라질 수 없게 했다.

**현금 검사는 확정을 막지 않는다.**
현금 기록은 그 달의 손익 숫자에 들어가지 않는다(§1). 등급을 올리면 마감이
통장 정리에 인질로 잡힌다. DB 가 이미 막는 것도 검사하지 않는다 — 영원히 0건인
항목은 목록만 채운다. 막지 못하는 것만 본다(원본 연결 없는 중복 의심 등).
