## PART B — 재고 가져오기 (P0)

### 7. 왜 최우선인가

상품이 1,067개인데 초기 재고를 화면에서 한 건씩 넣게 두면 아무도 재고 기능을
쓰지 않는다. 재고가 없으면 재주문도 못 돌고, 그러면 M048 전체가 장식이 된다.

### 8·9. 상품 열쇠

실제 DB 를 확인하고 정했다.

```
product.sku            PICK0785 형식, 1,036/1,065 채워짐, 전부 유일   ← 1순위
product.business_key   PROD-000000, 1,065 전부 유일                  ← 2순위
product.id             UUID                                          ← 3순위
```

`sku` 가 먼저인 이유: 사용자가 실제로 쓰는 번호다. `business_key` 는 우리가
만든 것이라 사용자 파일에 있을 가능성이 낮다.

**이름으로는 찾지 않는다.** 잘못 맞추면 엉뚱한 상품의 재고가 바뀌고 그대로
발주까지 나간다. 상품명 열만 있는 파일은 파일 수준에서 거부한다.

열 이름은 별칭을 받는다(`수량`/`재고`/`실사수량`/`quantity`). 사용자가 우리
표기법을 외울 이유가 없다.

### 10. 옵션

옵션이 여러 개인 상품에 옵션코드가 없으면 `AMBIGUOUS` 로 두고 **반영하지
않는다.** 임의로 하나를 고르면 엉뚱한 옵션의 재고가 바뀐다.

(현재 실 DB 에 variant 는 0건이라 실무에서는 아직 안 걸린다.)

### 11·12·13. 세 단계

```
ANALYZE   파일만 읽는다. DB 를 보지도 않는다
DRY_RUN   DB 와 대조해 무엇이 바뀔지 계산한다. 쓰지 않는다
APPLY     원장에 반영한다
```

`supplier_import.MODES` 와 같은 어휘를 재사용했다. 가져오기마다 다른 단계
이름을 쓰면 사용자가 매번 새로 배워야 한다.

API 기본값은 `DRY_RUN` 이다. 화면은 파일을 고르면 검토까지만 자동으로 돌고,
적용은 결과를 본 뒤에야 눌린다.

### 14·15·16. 수량을 덮어쓰지 않는다

| 상황 | 결과 |
|---|---|
| 원장 없음 | `OPENING +17` |
| 원장 14, 실사 17 | `ADJUSTMENT +3` |
| 원장 17, 실사 17 | `UNCHANGED` — 아무것도 안 만든다 |

Excel 의 17 을 잔량에 쓰지 않는다. 덮어쓰면 "왜 17 인가" 에 답할 수 없고, 두
사람이 동시에 올리면 한쪽이 조용히 사라진다.

### 재적용 안전장치

```
source_id = sha256(파일해시 : 상품 : 옵션 : 기준일)
```

`uq_inv_txn_source` 가 두 번째를 막는다. **실행 기록을 조회해서 판단하지
않는다** — 두 사람이 동시에 올리면 둘 다 "없다" 를 보고 둘 다 넣는다. DB
제약만이 확실하다.

파일명이 같아도 내용이 다르면 다른 파일이다(해시 기준). 같은 양식으로 **다른
날** 실사한 것은 새 원장 줄이다(기준일을 해시에 섞었다).

### 17. 수량 검증

```
0        유효하다. "실제로 0개" 를 말할 수 있어야 한다
음수      거부하지 않는다. 음수 재고는 예외 센터가 따로 잡는다
12.0     받는다 (Excel 이 정수를 float 로 준다)
12.5     거부한다 (재고에 소수점 개수는 없다)
빈 값     거부한다 — 0 과 다르다
```

### 18·92. 감사

**행마다 audit 를 남기지 않는다.** 1,000행이면 `audit_log` 가 1,000줄 늘어나고
사람이 한 변경이 그 속에 묻힌다.

행 단위 추적성은 원장이 이미 갖고 있다(누가·언제·무엇을·왜). 그래서 audit 는
**실행 단위**로 남기고, `inventory_import_run` 이 파일·해시·모드·결과를 갖는다.

파일 내용은 저장하지 않는다. 해시만 남긴다 — 보관하면 지워야 할 것이 하나 더
생긴다.

## PART F — 일일 리포트 자동화 (P1)

### 46·48. 기존 자동화 재사용

새 scheduler 를 만들지 않았다. 기존 `DAILY_REPORT` 정책/러너/worker 를 그대로
쓴다.

### 47. KST

`daily_report.report_date_now()` 가 `now_local()` 을 쓴다. UTC 로 날짜를 세면
한국 시간 오전 9시 이전에 돈 실행이 **전날** 리포트를 만든다 — 새벽 스케줄에서
정확히 그 일이 일어난다.

중복 판정 쿼리도 `(started_at AT TIME ZONE 'Asia/Seoul')::date` 로 자른다.

### 49·50. 하루에 한 번

판단 기준은 **성공한 실행이 오늘 이미 있었나** 다.

```sql
automation_run r JOIN automation_policy p ... JOIN automation_action a
WHERE p.automation_type = 'DAILY_REPORT'
  AND a.action_type = 'DAILY_REPORT_BUILT' AND a.outcome = 'REPORTED'
```

실패한 실행은 세지 않는다. 아니면 정산 조회가 한 번 터진 날은 리포트가 영영
없다.

리포트 전용 테이블을 만들지 않았다. 실행 기록은 이미 `automation_run` 에 있고,
두 군데 두면 어긋난다.

### 54·55·64. IN_APP 전달

`notification` 을 재사용한다 — 수신자 결정·중복 방지·읽음 처리가 이미 있다.
별도 `report_delivery` 테이블을 만들지 않았다.

```
dedupe_key = "daily_report:2026-08-11"
```

worker 가 두 번 돌아도 같은 날 알림이 두 번 가지 않는다. 매일 아침 같은 알림이
두 개씩 오면 사용자는 벨을 아예 안 본다.

M051 이 `enum_notification_kind` 에 `DAILY_REPORT_READY` 를 더했다. `kind` 를
자유 문자열로 바꾸면 오타가 새 종류로 조용히 들어간다.

수신 역할은 `ADMIN`/`OPERATOR`/`ACCOUNTING`. `READONLY` 에는 안 보낸다 — 볼
수는 있어도 손댈 것이 없어 알림이 소음이 된다.

### 56·62. 외부 전달

EMAIL 채널을 켜지 않았다. SMTP provider 가 실제로 없으므로 넣으면 보내지지도
않을 `QUEUED` 행만 매일 쌓이고 화면에는 "발송됨" 으로 보인다.

받을 사람이 없으면 `BLOCKED / NO_RECIPIENT` 다. **성공으로 만들지 않는다.**

### 53·59·60. 예외 센터와 한 몸

`daily_report.build()` 가 `exception_center.summary()` 를 호출한다. 각자 세지
않으므로 숫자가 갈라질 수 없고, 테스트가 두 값이 같은지 확인한다.

「오늘의 운영」에 카테고리 칩이 생겼고 누르면
`/operations/exceptions?category=INVENTORY` 로 간다. 예외 센터가 그 파라미터를
읽어 해당 묶음만 보여준다.

칩 문구는 건수가 아니라 **상태**에서 나온다 — `count=0` 이 "이상 없음"·"미연결"
·"설정 필요" 셋 다에서 나오기 때문이다.

## PART D — 발주 UI (P2)

`[발주 초안 만들기]` 다이얼로그를 추가했다. 지금까지 초안은 자동화나 MCP 만
만들 수 있었고, 사람이 판단했을 때 쓸 길이 없으면 결국 엑셀로 돌아간다.

### 28. 주 소싱처를 자동 확정하지 않는다

공급처를 사용자가 고른다. 자동으로 정하면 "왜 이 공급처로 나갔지" 를 나중에
설명할 수 없고, 이번만 다른 곳에서 사는 일이 실제로 흔하다.

### 29·30. 단가

상품 원가가 있으면 채우고 **"소싱 원가에서 가져옴"** 이라고 밝힌다. 없으면
비워 둔다 — 0 으로 채우면 0원짜리 발주가 나가고 그게 그대로 취득원가가 된다.

사용자가 고치면 그 표시가 사라진다.

### 31. 초안까지만

만들면 `DRAFT` 다. 공급처에 아무것도 보내지 않는다. 확정은 상세에서 별도 버튼 —
돈을 쓰기로 하는 결정을 만들기와 같은 동작에 묶지 않는다.

## PART H — 데이터 품질 (P4)

기존 `operation_issue` 스캐너의 `collect_candidates` 에 세 가지를 더했다. 중복
방지·자동 종료·사람이 닫은 것 보호는 스캐너가 이미 갖고 있어 그대로 얻었다.

| 항목 | 심각도 | 판단 근거 |
|---|---|---|
| `NEGATIVE_INVENTORY` | WARNING | 합계 < 0 |
| `PURCHASE_OVERDUE` | WARNING | 예상일 있음 + 지남 |
| `REORDER_DATA_INCOMPLETE` | INFO | 주 소싱처 또는 리드타임 없음 |

### 65·66. 임계값을 만들지 않았다

"재고 5개 미만"·"3일 이상 지연" 같은 기준은 없다. 그 숫자가 어디서 왔는지
설명할 수 없기 때문이다.

예상 입고일이 **없는** 발주는 지연이 아니다 — 늦었는지 알 수 없고, 그건
"정상" 이 아니라 "모름" 이다.

재주문 기한 경과는 이슈로 만들지 않는다. 매일 바뀌는 값이라 이슈 목록이
소음이 된다 — 예외 센터에서 본다.

`REORDER_DATA_INCOMPLETE` 는 재고를 **이미 관리 중인** 상품만 센다. 안 그러면
상품 마스터 1,067개가 통째로 이슈가 되고 아무도 안 본다.

## 이번에 찾은 결함

### `upsert_policy` 가 `str(None)` 을 UUID 로 넘겼다

`actor_user_id=None` 이면 `'None'` 이라는 문자열이 UUID 컬럼으로 가서
`DataError` 가 났다. 에러 메시지가 원인을 가리키지 않아 찾기 어렵다. 고쳤다.

### 테스트 스위트를 동시에 두 번 돌리면 안 된다

같은 테스트 DB(`picksome_ops_test`)를 쓰는 pytest 프로세스가 둘이면 12~21건이
무작위로 실패한다. 이번에 그렇게 돌려서 실패를 봤고, 단독 실행에서는 **972건
전부 통과**했다.

CI 에서 병렬로 돌릴 계획이면 DB 를 분리해야 한다.
